# 功能模块解耦与流程梳理计划

> 仓库：flash-sim（FLASH 4.8 Python 接口）｜版本基线：0.1.11｜日期：2026-10-24
> 范围：① 根目录部署/测试模块 ② `flash/flash_run` 执行方案 ③ `flash/scenarios` 子场景调用

---

## 0. 结论

三个模块**表面上已经分层**（见 README「功能模块地图」），但实际是：

- **三条并行且互不复用的执行路径**
- **两套部署入口**（`start_flash.py` 与 `deploy/hpc_deploy/run_all.py`）
- **一处层次倒置**（`deploy/` 依赖 `flash.scenarios.*`）
- **六套子场景调用契约**

且已积压 **10 个真实回归**，其中一条会让「FLASH 根本没跑」被报成成功。

核心病灶**不是"缺抽象"，而是"抽象已存在、落地不全"**：

| 已有抽象 | 现状 |
|---|---|
| `run_scenario()` 统一入口 | 全仓库 **0 次真实调用**（死 API） |
| `slurm_control.CommandExecutor` | `HpcRunner` 不用它，自写 `sacct` 轮询 |
| `_wh_common` 平台感知 venv helper | `run_all.py` 不用它，硬编码 `C:\Users\...python.exe` |
| `fetch_policy`（chk-only 唯一源） | `HpcRunner.download()` 完全不用，只下 3 个固定文件 |

⇒ 本计划策略：**先修回归 → 收敛到既有单一事实源 → 用护栏锁死回退**。不造第二层抽象。

## 2. 目标架构

### 2.1 边界铁律

```
deploy/           部署层：造包 / 离线安装 / 超算部署链
                  规则：禁止 import flash.scenarios；允许 import flash.flash_run
flash/flash_run/  执行层：目标解析 / 四模式 / SSH / slurm / 回收 / 装置配置
                  规则：禁止 import flash.scenarios
flash/scenarios/  场景层：物理声明 + 参数覆盖 + 分析回调
                  规则：禁止 ssh/sbatch/paramiko/["wsl"/分区表/装置绝对路径
flash/input_gen/  输入生成层：无运行细节
```

> **规则修正**：旧文档「deploy 不依赖上两层」已被 6 个脚本事实上打破，
> 且无法与"单一事实源"同时成立 ⇒ 收窄为：`deploy → flash_run` 允许，
> `deploy → scenarios` 禁止。这是精确化，不是放宽。

### 2.2 四目标模型

`EXEC_TARGETS = ("local", "wsl", "hpc-remote", "hpc-insitu")`

| 目标 | executor | 传输 | 作业控制 |
|---|---|---|---|
| `local` | `LocalExecutor`（bash -c） | 同文件系统 | 直接 `bash run_flash.sh` |
| `wsl` | `WslExecutor`（`wsl.exe -d D -- bash -lc`） | `/mnt/<drv>` | 同 local |
| `hpc-insitu` | `LocalExecutor` | `copy2` | `slurm.run_job_chain` |
| `hpc-remote` | `SSHExecutor` | `sftp` | `slurm.run_job_chain` |

⇒ hpc-insitu 与 hpc-remote **共用同一套作业控制**，只换 executor 与传输层。

### 2.3 平台自适应判定表（`auto` 默认）

| 序 | 判据 | 命中 |
|---|---|---|
| 1 | `--mode` 显式 | 该校验值（须 ∈ 场景 `allowed_modes`） |
| 2 | `sbatch` + `sacct` + `sinfo` 三者齐备 | `hpc-insitu` |
| 3 | `os.name != "nt"` | `local` |
| 4 | Windows 且有 `wsl` | `wsl` |
| 5 | 以上皆否 | **报错**，打印判定轨迹与修复建议 |

判定后再与场景 `allowed_modes` 求交，交集为空即报错（例：SNB 在 Windows 上
只允许 `hpc-remote`/`hpc-insitu` ⇒ 明确拒绝，而不是悄悄本地跑）。

**兼容性**：`RUN_MODES` 三元组保持不动，`EXEC_TARGETS` 为新增 canonical，
旧名经 `RUN_MODE_ALIASES` 桥接 ⇒ `test_scenarios_modes.py:39` 断言零改动。

### 3.2 新增单一事实源：`flash/flash_run/env/venv_paths.py`

纯 stdlib（`os/sys/pathlib/typing`），**零 flash import**，供部署侧在 `pip install`
之前按文件路径加载。API：

```python
repo_root(start=None) -> Path | None      # 向上探测 pyproject.toml + start_flash.py
venv_dir(root, kind="local"|"hpc") -> Path
venv_python(root, kind) -> Path | None    # FLASH_VENV_DIR > 平台后缀 > 旧 .venv
candidates(root, kind) -> list[Path]      # 供报错与 --check-env
require_venv_python(root, kind) -> Path   # 失败即 raise（含可操作提示）
```

关键约束：`kind` 用 `local`/`hpc` 而非平台名（两维度正交，WSL 上尤甚）；
`repo_root()` 失败返回 `None` 但**绝不回落 `sys.executable`**——历史 bug 正是
该回落把「venv 找错」伪装成「h5py 未安装」。

### 5.2 护栏纪律（本项目两次踩空的教训）

1. 禁 `^from flash...` **行首锚定** grep——部署层 6 处导入全在函数体内，会全数漏检并显示"通过"；须用 `^\s*(from|import)\s+` 或 AST。
2. 禁手写文件条数——清单必须由 `git grep -l` 生成（本轮 7 vs 6、20 vs 8 两处基数均被纠正）。
3. 每条规则必须有**负向样本**，且样本须放在**与真实违规相同的缩进层级**。
4. **未证明会失败的护栏不算护栏**；报喜不报忧的护栏比没有更危险。

> 典型实例：`deploy/test_offline_install.py` 的 17 个 `test_*` 中，8 个带
> `root: Path` 形参（pytest 下必 ERROR），9 个走 `check()` 而该函数**只
> `append`+`print`、不做断言**，全文件 `assert` 计数为 0 ⇒ 「183 项自检」
> 在 pytest 下是 9 空绿 + 8 报错。因此 `testpaths` 加 `deploy` **之前必须先重构**。

### 8.3 本轮暴露的流程缺陷（已修，见 §4 增补表）

最值得记录的是 **G12**：`sbatch` 前的 `module load` 耗时超过封装层的 30 s 超时，
于是出现「作业在算、封装层报 FAIL」。这类**假失败**比真失败更危险 ——
它会诱导重复提交，且在日志里留下与实际相反的结论。修法是：
超时后**回查 `squeue`**（按 job-name），已提交则继续等待。

> 通用教训：任何"提交类"操作，超时**不等于**未提交。判定必须来自
> 状态查询（`squeue`/`sacct`），而不是调用是否返回。
