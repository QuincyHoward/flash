> 按本文可复现地从零搭出任意同类场景。

## 1. 第一步：写薄驱动（唯一的自有文件）

新建 `t006/run_t006.py`，内容是**编排**而非实现：

```
run_t006.py
  ├─ generate → SNB/SNB/scripts/generate/gen_scene.py
  ├─ run      → SNB/SNB/scripts/run/run_scene.py
  ├─ check    → SNB/SNB/scripts/analysis/chk_probe.py
  └─ plot     → SNB/SNB/scripts/analysis/compare_4way.py
```

### 1.1 核心模块定位（不写死层数）

```python
def _find_snb_core() -> Path:
    for anc in [HERE] + list(HERE.parents):
        for cand in (anc / "SNB", anc.parent / "SNB"):
            if (cand / "scripts").is_dir() and (cand / "source").is_dir():
                return cand
    raise SystemExit("[X] 未找到 SNB 核心模块")
```

**为什么**：场景目录可能被整体搬迁或改层深；写死 `parents[3]` 会脆弱。

### 1.2 把"血泪教训"写成护栏

t005 的失败（`dtmax=2e-12` → 崩塌）与作者原版的陷阱（`call RadTrans` 被注释）
都在 `preflight()` 里做成**硬拒绝**，而不是靠注释提醒：

```python
DTMAX_REQUIRED = 2.0e-14
DTMAX_GUARD = 1.0e-13             # 超过即拒绝
DRIVER_VARIANT_REQUIRED = "radon"
```

> **原则**：能自动拦截的错误，不要留给下一次的自己去踩。
> 错误信息里要带上**后果的具体数字**（ρmax 12.11→0.26），比"请勿修改"有用得多。

### 1.3 分层输出

`scene/`（生成物，可删重建）、`images/`、`results/`、`logs/` 分开 ——
便于"结论"与"中间产物"分离，也便于 `scene/` 随时重新生成而不丢结果。

## 2. 第二步：生成场景

```bash
$PY run_t006.py --stage generate
```

内部等价于：

```bash
$PY <SNB>/scripts/generate/gen_scene.py --out t006/scene \
    --legs snb,flsh --radiation both \
    --driver-variant radon \
    --nxb 128 --iprocs 8 --tmax 8e-10 --dtmax 2e-14 \
    --chk-dt 5e-11 --plt-dt 4e-10 \
    --verify-keys-against <SNB>/source/example/flash.par
```

### 2.1 必须看的两项自检输出

| 自检 | 期望 | 不满足的后果 |
|---|---|---|
| **受控性自检** | 同腿两状态差异键 **仅** `basenm/log_file/rt_useMGD/useOpacity/useRadTrans`；跨腿仅腿标识 | 四腿对比不再是单变量对照 |
| **键集差分校验** | `183 键; 缺(物理相关) 0` | 漏边界键 → SNB 腿失真（`Te` 异常偏高、靶被打散） |

> ★ **`--verify-keys-against` 是强制规范**：从零生成 par 极易漏掉
> "看似与主题无关、实则决定稳定性/守恒"的键。
> 实测教训：曾因缺 6 个 `rt_mgd*BoundaryType` + 6 个 `diff_ele*BoundaryType`
> 导致 SNB 腿失真，而 FL-SH 腿因不依赖这些键而**正常** —— 极难察觉。

### 2.2 本场景的生成产物（实测）

```
sim_snb/flash_input/   18 文件   (9 覆盖 F90 + Config/Makefile + 6 Simulation_*/mgd_qesh + 2 cn4 + par)
sim_flsh/flash_input/  10 文件   (Config/Makefile + 4 Simulation_*/mgd_qesh + 2 cn4 + par)
```

SNB 腿的 `diff_advanceTherm.F90`/`Driver_evolveFlash.F90` 等来自
`source/snb_package/`，其中 `Driver_evolveFlash.F90` 被 **radON 变体覆盖**
（生成日志会打印 `[!] 已应用诊断变体: radon→Driver_evolveFlash.F90`）。

## 3. 第三步：短时验证（必做）

```bash
$PY run_t006.py --smoke          # tmax=1e-11
```

**目的**：用最小代价暴露配置错误（setup 标志、群数、表、par 键）。
setup + make 是主要耗时（SNB 侧约几分钟），但**只需做一次**，
后续正式跑用 `--skip-setup --skip-make` 复用。

**通过判据**（自动由 `--stage check` 给出，本场景实测）：

```
[OK] dt 全程钳位于 dtmax = 2.000000e-14 (最大相对偏差 0.00e+00)
[OK] ρmax: 1.0400 → 1.0400
✓ 健康 (dt 钳位正确)
```

短时阶段 ρmax 尚未增长是**正常**的（1e-11 s 时烧蚀还没启动）。

## 4. 第四步：正式运行四腿

```bash
$PY run_t006.py --stage run --tmax 0.8e-9       # 首次（含 setup/make）
# 或改 par 后复用二进制:
$PY run_t006.py --stage generate
$PY run_t006.py --stage run --skip-setup --skip-make
```

**运行顺序**：`snb/radon → snb/radoff → flsh/radon → flsh/radoff`。
每侧的**第一条腿**负责 deploy+setup+make，第二条腿自动
`--skip-deploy --skip-setup --skip-make`（只换 par，输出 tag 不同所以不覆盖）。

**每腿结束自动做健康检查**（`run_scene.py` 内建，读 chk 的 `dt`）：

```
[OK] dt 全程钳位 = 2.000e-14 ✓
[OK] [snb/radon] 收集 OK (17 帧) — 墙钟 1405.9 s
```

## 5. 第五步：健康检查（独立复核）

```bash
$PY run_t006.py --stage check
```

等价于对四个腿目录各跑一次：

```bash
$PY <SNB>/scripts/analysis/chk_probe.py \
    --dir t006/scene/flash_output/sim_snb/radon \
    --expect-dtmax 2e-14 --brief
```

**这是本文档最重要的判据**。`dt` 的三种形态对应三种结论：

| `dt` 形态 | 结论 |
|---|---|
| 全程 = 2.000e-14（钉死） | ✓ `dtmax` 生效，配置正确 |
| 单调增长（如 2.88e-14 → 4.56e-14） | ✗ `dtmax` 未生效 → 即将/已经崩塌 |
| 随 `dtmin` 坍缩 | ✗ 早期瞬态失稳 |

**退出码**：0 = 健康，1 = 异常，2 = 无法判定。可用于 CI/批处理。

## 9. 常见问题速查

| 症状 | 首查项 |
|---|---|
| SNB 腿 ρmax 冲高后崩塌、质量 NaN | **`dtmax` 是否 = 2e-14**（读 chk 的 `dt`） |
| SNB 腿 `trad` 不涨（与 rADOFF 无区别） | **`driver-variant` 是否 = radon** |
| `Te` 异常偏高、靶被打散 | 是否漏了 `rt_mgd*BoundaryType` / `diff_ele*BoundaryType`（跑键集差分） |
| `MGD Error: Bad group boundary` | `rt_mgdNumGroups` 与 `mgd_meshgroups` 是否一致；`rt_mgdBounds` 是否 N+1 个 |
| 启动即 `Negative 3T internal energy` | `dtmax` 过大；或 cn4 表温度下限高于初值 |
| 第 13 个 `plot_var` 无效 | `plot_var` 编译期硬上限 = 12 |
| 挂死 | `mpiexec -n` 是否严格等于 `iProcs` |
