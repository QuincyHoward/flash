## 1. 症状

SNB 侧两条腿出现非物理行为，而 **FL-SH 侧两条腿全程正常**：

| 观测 | SNB 腿 | FL-SH 腿（对照） |
|---|---|---|
| ρmax 演化 | 冲高到 ~10.5 后**崩塌到 0.26** | 单调升至 6.7，稳定 |
| 总质量 | **相对漂移 0.59**（守恒破裂） | 漂移 0.014 |
| 烧蚀速率 Ṁ | **3.4e7**（比正常大 ~65×） | 5.0e5 |

**关键特征**：崩塌**不是** FL-SH 与 SNB 的模型差异，而是 SNB 腿单独失真
→ 指向 SNB 特有的代码路径或配置项。

**最早出现差异的时刻**：**第 1 帧（0.05 ns）就已不同**
（t004 ρmax=1.738337 vs t006 ρmax=2.845451，差 1.637×）
→ 说明是**初始/求解器配置**差异，而非后期数值累积。

## 2. 结论的三次演进（前三版均为不完整/错误）

记录在此，避免重蹈。**教训见 §7。**

### ❌ v1：「`diff_advanceTherm.F90` 各向同性分支限流器被注释」

| 项 | 内容 |
|---|---|
| 假说 | 非各向异性分支里的限流器调用被注释 → 限流失效 → κ 无界 |
| 表面支持 | 该分支确有被注释的调用（与各向异性分支不对称） |
| **推翻依据** | **t004 与 t005/t006 的该文件逐字节完全相同**（md5 `c2dfe4f5…`）→ 不可能解释差异 |
| 残留价值 | 该不对称**是真实存在的实现差异**，可作后续独立议题，但**不是本次根因** |

### ❌ v2：「radON 驱动（恢复 `call RadTrans`）导致崩塌」

| 项 | 内容 |
|---|---|
| 假说 | radON 恢复辐射推进 → 多一条能量通道 → 500 ps 后崩塌 |
| 表面支持 | t005 用了 radON 驱动且崩塌 |
| **推翻依据 ①** | 改回 `--driver-variant none` 后**仍然崩塌** |
| **推翻依据 ②** | **t004 实际编译运行的部署单元就是 radON 变体**（md5 `9fe4e2ee…`，18,425 B）→ radON + 正确配置 = 成功 |
| **推翻依据 ③** | 崩塌两腿（radON/radOFF）幅度几乎相同 → 与辐射无关 |

### ❌ v3：「`dtmax` 用成 `2e-12`」

| 项 | 内容 |
|---|---|
| 假说 | `dtmax=2e-12` → `dt` 增长到 4.6e-14 → 越过稳定阈值 → 崩塌 |
| 表面支持 | t004 实际 `dt` 钉在 2e-14；t005 的 `dt` 增长到 4.6e-14 |
| **推翻依据** | **t006 的 `dtmax` 正确为 2e-14（chk 实测全程钉死），却依然崩塌**（ρmax→0.25） |
| 正确成分 | `dtmax=2e-14` **确实是必要条件**（t005 的 dt 增长是同一失稳的另一表现），**但不是充分条件** |

### ✅ v4（最终）：「`gr_hypreUseFloor` 退回默认 `.true.`」

见 §0。**单键 A/B 实测：修复后与成功基线逐位相同。**

## 3. 决定性证据

### 3.1 参数回显差分法（最强手段）

FLASH 启动时会把**全部运行时参数**回显到日志（约前 1400 行）。
对两个日志做参数级差分，可绕过"par 文本可信度"的全部争议：

```
解析 t004/verify_radon 日志: 1231 个参数
解析 t006 日志          : 1231 个参数
取值不同: 10 个
```

排除命名/注释/IO 类后，**剩下 5 个物理候选**：

| 键 | t004 | t006 | 是否根因 |
|---|---|---|---|
| **`gr_hypreUseFloor`** | **F** | **T** | ✅ **是**（A/B 证实） |
| `UnitSystem` | CGS | none | ❌ 否（变体 A 未加它也已逐位复现） |
| `pc_unitsBase` | "CGS" | (缺) | ❌ 否（同上） |
| `ed_useLaserIO` | T | F | ❌ 否（同上） |
| `ed_laserIOMaxNumberOf{Rays,Positions}` | 64/10000 | -1 | ❌ 否（同上） |

> ★ **`UnitSystem` / `pc_unitsBase` / `ed_*IO` / `gr_hypreUseFloor` 都曾被
> `_KEY_DIFF_IGNORE` 放行** —— 其中最后一个正是根因。
> 说明"忽略清单"绝不能凭直觉，必须靠 A/B 实测确定无害。

### 3.2 chk 实测 `dt`（用于排除 `dtmax`）

| 运行 | par 写的 `dtmax` | chk 实测 `dt` | ρmax 末值 | 结果 |
|---|---|---|---|---|
| t004 成功 | 2e-12（文本） | **2.000e-14 钉死** | **12.111** | ✅ |
| t006 崩塌 | 2e-14 | **2.000e-14 钉死** | **0.255** | ❌ |
| t005 崩塌 | 2e-12 | 2.88e-14 → **4.56e-14 增长** | 0.255 | ❌ |

→ **`dt` 钳位正确 ≠ 结果正确**。`dtmax` 只是必要条件之一。
（旧版本文曾据此断言"根因是 dtmax"，v4 已更正。）

### 3.3 排除项汇总

| 假说 | 排除方式 | 结论 |
|---|---|---|
| F90 覆盖件差异 | 部署单元 16 个文件穷尽 md5：**全部相同** | 排除 |

## 4. 机理

`gr_hypreUseFloor` 是 **HYPRE 隐式扩散求解器**的 floor 开关：

- SNB 的多群非局域热流经**隐式扩散**求解（每步解一个大线性系统）；
- FLASH 该键**默认 `.true.`**（对解/系数取 floor，避免病态矩阵）；
- 对本场景的陡峭瞬态，floor 会**改变解** → 电子热流偏大 → 靶被过度压缩
  → ρmax 虚高到 ~10.5 后崩塌（质量不守恒）；
- 置 `.false.` 后求解器按原样求解 → 结果与物理预期一致。

**注意**：这**不是**"分辨率越高越不稳"，也**不是**单纯的时间步问题。

## 5. 修复做法

### 5.1 生成器侧（已修）

```python
# snb_params.py — CONDUCTION 块新增
"gr_hypreUseFloor": False,   # ★★★ 决定性键; FLASH 默认 .true. 会使 SNB 解失真

# gen_scene.py — 从忽略清单移除, 并加硬校验
NUMERIC_CRITICAL_KEYS = (
    "gr_hypreUseFloor", "diff_eleFlMode", "diff_eleFlCoef",
    "diff_thetaImplct", "dt_diff_factor", "dtmax", "rt_mgdNumGroups",
)
```

`verify_keys_against()` 现在会**独立于忽略清单**检查 `NUMERIC_CRITICAL_KEYS`，
缺失即报错 —— 该键再也不可能被静默放行。

### 5.2 运行前确认

```bash
grep -nE "^(gr_hypreUseFloor|dtmax|tmax|rt_useMGD|useRadTrans)" <objdir>/flash.par
```

**最可靠的核对方式**：与参考日志做**参数回显差分**（§3.1）。

### 5.3 运行后确认（chk）

```python
import h5py
with h5py.File("xxx_hdf5_chk_0016", "r") as f:
    for row in f["real scalars"][()]:          # 复合 Dataset, dtype.names=('name','value')
        if row["name"].decode().strip() == "dt":
            print(float(row["value"]))          # 期望 2.000e-14
```

**通过判据**：`dt` 全程 = 2.000e-14 **且** ρmax 单调升至 ~12（不出现跌崖）。

> ⚠ `dt` 钳位正确**只是必要条件**；必须同时检查 ρmax 与总质量。

## 7. 教训清单（可迁移）

1. ★★★ **"键集校验通过" ≠ "配置正确"。**
   忽略清单（`_KEY_DIFF_IGNORE`）一旦放行了物理相关键，校验就形同虚设。
   → **忽略清单必须靠 A/B 实测确定**；并另设"数值敏感键硬名单"独立把关。
2. ★★★ **`dt` 钳位正确 ≠ 结果正确。** `dtmax` 只是必要条件。
   必须同时检查 **ρmax 走势**与**质量守恒**。
3. ★★ **用"参数回显差分"做配置溯源**，比读 par 文本可靠得多
   （par 可被覆写；日志回显的是**实际生效值**）。
4. ★★ **不要用"差异文件"或"相关性"直接当根因。**
   先穷尽哈希比对（v1 的教训），再做单变量 A/B（v2 的教训）。
5. ★★ **差异出现在第 1 帧 → 找初始/求解器配置**，不要往后期数值累积上想。
6. **单变量 A/B 是唯一能"钉死"根因的手段**：
   本案例中只有它把 5 个候选键收敛到 1 个（并且是逐位复现级别的证据）。
7. **不要因"结论看起来合理"就停止验证** —— v1/v2/v3 都"看起来合理"。
