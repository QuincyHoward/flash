# 06 — 分享与保密规则

**适用范围**：`flash/scenarios/private/SNB/` 下的一切内容。
**核心原则**：**分享方法，不分享实现。**

---

## 1. 分类规则

| 类别 | 判定 | 处置 |
|---|---|---|
| **F90 源码**（SNB 覆盖文件及其任何变体） | 实现本体 | ❌ **不分享** |
| **会写入 / 生成 F90 的 py 脚本** | 脚本即等价于源码 | ❌ **不分享** |
| **逐字引用 F90 算法片段的文档** | 引用等同分享 | ❌ **不分享** |
| 场景 par（参数配置） | 方法 | ✅ 分享 |
| 运行 / 分析 / 绘图 py 脚本 | 方法（不含 F90） | ✅ 分享 |
| 说明文档 / 流程文档 | 方法 | ✅ 分享 |
| 初始条件布局、材料、激光时序 | 物理设置 | ✅ 分享 |
| 凭据 / 密钥 / 账号 / token | 敏感 | ❌ **永不入库** |

### 明确列入「不分享」的具体项

| 路径 | 原因 |
|---|---|
| `**/variants/*.F90` | SNB 源码派生变体 |
| `**/flash_input/*.F90`、`**/flash_output/**` | 生成/输出的 F90 与产物 |
| `SNBtest/src/**` | FLASH 源码树快照（另有 License §3 约束） |
| `**/scripts/generate/make_therm_variant.py` | **写出 F90 变体**（已由 `tools_local/make_variants.py` 取代） |
| `**/scripts/generate/gen_t003_inputs.py`、`gen_t004_inputs.py` | **复制 F90 + 内嵌 Fortran 片段** |
| `**/docs/snb_source_diagnosis.md` | **逐字引用算法片段** |
| `SNB/SNB/source/`、`SNB/SNB/variants/`、`SNB/SNB/tools_local/` | 本地保留层（实现包 / 变体 / F90 生成器） |

## 1b. 目录分层（核心模块特有）

`SNB/SNB/` 同时是"可分享文档集"与"F90 实现包本地仓库"，故按目录显式分层：

| 层 | 目录 | 入库 | 说明 |
|---|---|---|---|
| 可分享层 | `README.md` `docs/` `scripts/` `manifest.json` | ✅ | 文档、参数、生成器、运行驱动、检查器 |
| **本地保留层** | `source/` | ❌ | 作者实现包 + 参考版 + 表 + 示例 par |
| **本地保留层** | `variants/` | ❌ | F90 诊断变体 |
| **本地保留层** | `tools_local/` | ❌ | **会写入 F90** 的脚本 |

> ★ `tools_local/` 是"目录闸门"存在的直接理由：其内容是 `.py`
> （扩展名在放行列表内），但**会写入 F90 源码**，等价于源码本身。
> **只按扩展名做白名单/黑名单是挡不住的**，必须整目录排除。

## 2. `.gitignore` 机制说明

本仓库采用**「全局忽略 + 白名单放行」**两层机制：

```gitignore
# 本地保留层 (SNB/SNB 内) —— 整目录排除
source/
variants/
tools_local/
*.F90
*.f90

# 第一层: 整个 SNBtest 默认忽略
**/SNBtest/**
# 第二层: 只放行"非源码"类型
!**/SNBtest/Test/**/*.py
!**/SNBtest/Test/**/*.md
!**/SNBtest/Test/**/*.par
!**/SNBtest/Test/**/Config
!**/SNBtest/Test/**/*.sh
# ... (Makefile / cn4 / bat 等)
# 第三层: F90 一律不放行
**/*.F90
**/*.f90
**/Test/t00*/variants/
```

### ★ 历史教训（务必保留的意识）

曾用 `!**/SNBtest/Test/**/*.F90` 反向放行 F90，"当时想着场景自带的
`Simulation_*.F90` 也许要分享"。后果：

```
$ git add -n --all | grep -i '\.f90'
add '.../Test/t003/variants/Driver_evolveFlash_radON.F90'
add '.../Test/t003/variants/diff_advanceTherm_limiterON.F90'
add '.../Test/t004/variants/Driver_evolveFlash_radON.F90'
```

**即：SNB 源码派生变体本会被提交。** 已修正为不放行任何 F90。

**根因**：白名单按**文件类型**放行时，只要留下了"源码类型"的口子，
任何位置的源码都会漏出去；`flash_input/` 的目录级忽略只能挡住那一个目录。

**准则**：
> 白名单**只放行非源码类型**（`py` / `md` / `par` / `Config` / `sh`）；
> 对源码类型（`F90` / `f90` / `c` / `h` 中属版权材料者）**一律全忽略，不开任何口子**。

## 3. 提交前自检（**强制**）

```bash
python flash/scenarios/private/SNB/SNB/scripts/check_share_safety.py
```

脚本执行双重校验：

| 校验 | 方法 | 通过判据 |
|---|---|---|
| ① 类型闸门 | `git add -n --all` 干跑，筛出会被提交的源码类文件 | **0 个** |
| ② 内容闸门 | 扫描待提交文本文件里的 Fortran 特征串 / 密钥模式 | **0 命中** |

有任一命中即 **exit 1** 并打印清单 → 按本文件第 1 节处置后再提交。

### 为什么两重都需要

- 只看 ①：把 F90 内容**粘进 md/py** 就绕过了（类型是放行的）；
- 只看 ②：`.gitignore` 配错时（如历史上的 `!*.F90`）源码类型根本进不了扫描列表。

---

## 4. 密钥 / 凭据

- 凭据文件（账号、密码、token）**永不入库**，`.gitignore` 需显式列出；
- 脚本中**禁止硬编码**明文密钥，改为从凭据存储读取；
- **AI / 脚本不得修改用户凭据内容**，只能读取；
- 分享文档里如需示例，用**占位符**（如 `<YOUR_ACCOUNT>`）。

## 5. 上游许可约束（FLASH License §3）

> "Users of the FLASH Code are not free to re-distribute the FLASH Code,
>  or any of its components, outside the Center."

因此以下内容**均不得**通过任何公开平台分发：

- FLASH 源码树快照、源码补丁；
- 官方示例场景的源码 / 表格 / 配置全文；
- 由 FLASH 源码派生的覆盖文件。

**可以**分享的是：**你自己写的**参数配置、驱动脚本、分析脚本、
以及描述方法论的文档。

---

## 6. 与 Git 远端的历史泄漏处置

若发现敏感内容**曾经**进入过提交历史：

1. **仅删除文件并提交是不够的** —— 历史里仍在；
2. 需重写历史（`git filter-repo` / `filter-branch`）**或**
   直接删除远端仓库重建后重新推送；
3. 重写后通知所有协作者重新克隆；
4. 若含**真实凭据**，立即**轮换密钥**（历史清理不等于密钥安全）。

## 7. 检查清单（提交前逐条勾）

    - [ ] `check_share_safety.py` 通过（exit 0）
    - [ ] **待提交集合 = 暂存 ∪ 未跟踪 ∪ 已修改**（脚本已如此实现）；
          手工核对请用 `git status --porcelain`，**不要只用 `git add -n --all`**
          （后者看不到已 `git add` 的内容 —— 见 §8 漏洞 B）
    - [ ] `git ls-files` 中无任何 `*.F90` / `*.f90` / `*.f95` 等源码类
    - [ ] 无 `variants/`、`flash_input/`、`flash_output/`、`src/` 内容
    - [ ] 待提交的 `md` / `py` 中无 Fortran 算法片段
    - [ ] 无凭据 / 密钥 / 账号明文
    - [ ] 新增文件类型已确认属于"非源码"
    - [ ] 若曾泄漏 → 已重写历史并轮换凭据

## 8. ★★ 对抗性复核与补漏（2026-09-12）

**方法**：故意造违规样本（`leak.F90` / `leak.f95` / 把 F90 逐字粘进 `leak.md`），
分别处于"未暂存"与"已 `git add`"两种状态，看检查器是否拦得住。

### 查出两个漏洞（均已修复）

| # | 漏洞 | 复现 | 后果 | 修复 |
|---|---|---|---|---|
| **A** | **扩展名白名单漏项**：类型闸门只列了 `.f90/.f/.for/.f77/.ftn/.inc`；内容闸门又用**文本白名单**（未列出的后缀**静默跳过**） | 造 `leak.f95`（内容为 Fortran 源）→ **两个闸门都不报**，`git add -n --all` 却会选中它 | 一个 Fortran 源文件可**原样提交进公开仓库** | ① 类型闸门补齐 `.f95/.f03/.f08/.fpp` 等；② **内容闸门改为"二进制黑名单"** —— 除源码类与明确二进制外**一律当文本扫**（+NUL 字节嗅探 + 体积上限），不再有"未知即放行" |
| **B** | ★★★ **已暂存内容对检查器不可见（致命 fail-open）** | 未暂存的 `leak.md`（含逐字 F90）→ 拦住 rc=1；**一旦 `git add` 之后再跑 → rc=0「安全可提交」** | 暂存内容**正是将要提交的内容**，却完全未被检查 → 源码可能被推上公开远端 | 待提交集合改为 **`git diff --cached` ∪ `git ls-files --others` ∪ `git ls-files --modified`** 三路并集 |

另修：**git 查询失败时原先返回 0（"安全"）** → 改为 **fail-closed**（返回 2 = 环境问题，拒绝放行）。

### 复核结论（修复后）

```
① 类型闸门  leak.f95  → [X] 源码/二进制类型 .f95        ✓ 拦住
② 内容闸门  leak.md（已暂存）→ [X] Fortran 声明 / end subroutine / call RadTrans(   ✓ 拦住
```
- `git ls-files` 中被跟踪的**源码/二进制文件数 = 0** ✓
- `git check-ignore` 实测：`source/*.F90`、`flash_input/*.F90`、`tools_local/*.py`、
  `variants/*.F90` **全部被忽略** ✓

> ★ **可由检查器挡住的**是"内容/类型"；**挡不住的是"作者自己把源码贴进 md"** ——
> 那条只能靠**人工审阅**（§7 清单里"待提交 md/py 中无 Fortran 算法片段"一项不可省）。

### ★ 新增扩展名时必须回来补的地方
`check_share_safety.py` 的 `FORBIDDEN_SUFFIXES`（源码/二进制）与
`BINARY_SUFFIXES`（确实不需扫的二进制）。**默认是"扫"，不是"放行"。**
