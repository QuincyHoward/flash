# 超算并行提速方案计划（SandwichTxN / 1D 激光烧蚀族场景）

- 日期: 2026-10-31
- 依据: 《执行统计报告_SandwichTxn_2026-10-31.md》实测数据（作业 4935059 + WSL runs/000001）
- 目标: 未来并行提交**多个**场景/参数扫描任务时，把 v5_192 节点利用率和总吞吐提升一个量级

---

## 1. 现状与瓶颈证据

实测（作业 4935059, ntasks=4, v5_192）:

| 事实 | 数据 | 影响 |
|---|---|---|
| 整节点分配 | AllocCPUS=48（分区 SelectTypeParameters=NONE，4 task 亦占满节点） | 44/48 核空转，**节点利用率 8.3%** |
| 每 rank 资源 | 1 核 + 63.7 MiB RSS | 1D 场景本质是单核小内存负载 |
| 单 rank 无多线程收益 | flash4 CPU 400%/4 = 每核打满，无 HT 增益 | 加 rank 是唯一并行维度 |
| 排队几乎为零 | Submit→Start 0 s（idle 274 节点） | 提速重点不在排队，在**打包** |
| 编译段 91 s/作业 | make -j4 被钳制（make_jobs_max） | 批量可摊薄为 ~0 |
| 归档 196 MB/作业 | 单线程写共享盘 | 批量时 IO 可交错 |
| 本地单核反而快 1.8× | WSL 65.7 步/s vs 超算 36.0 步/s | 超算的定位 = 大规模并发吞吐 |

**结论**: 单作业加核不是方向（1D 域最多 nblockx=8 初始块、~50–98 叶块，4→8 rank 收益有限且需实测）；**方向是把 48 核节点"装满"多个 4-rank 场景实例**。

## 2. 三条路线评估

### 路线 A：单作业多场景打包（★ 推荐，近期实施）
一个 sbatch 作业内：编译**一次** → 串行/并行运行 N 个场景（每个 4 rank，并发 12 路 = 48 核）→ 按场景分目录归档。

- 预期收益: 节点利用率 8.3% → **~95%+**；12 个场景的总墙钟 ≈ 1 个场景（~12 min）+ 少量 IO 交错开销；吞吐 **×12**
- 内存核算: 12 × 255 MiB ≈ 3 GB ≪ 187 GB，无压力
- 归档 IO: 12 × 196 MB = 2.3 GB/作业，tmpfs 写入快，归档段可并行 tar
- 依赖改造: `flash_run` 模块（见 §3）

### 路线 B：作业数组 `sbatch --array`（不推荐，待验证）
每个数组元素 = 一个独立作业。若分区按 CPU 消耗分配（CR_CPU），调度器可将多个元素拼到同一节点。

- 实测障碍: 本分区 4-task 作业即 AllocCPUS=48（整节点记账）⇒ 数组元素大概率各自独占节点，**无法拼节点**
- 保留价值: 若集群日后改为 CPU 级 consumable，此路线零代码改动；可提交 `--ntasks=4 --mem=8G` 试验作业验证 AllocCPUS 是否 =4
- 判定成本: 1 次试验提交，10 分钟

### 路线 C：提高单作业 ntasks（辅助选项）
4 → 8 rank（nblockx=8）：预期扩展效率 70–90%（guardcell 同步 + AMR 负载不均），单场景 10 min → ~6–7 min。

- 定位: 只对**单场景延迟敏感**的任务有意义；吞吐场景下不如路线 A（8 rank 占节点更浪费）
- 行动: 一次性扩展性试验（ntasks=8 vs 4, 记录步速），不作为主路线

## 3. flash_run 模块改造清单（路线 A 落地）

| # | 改造点 | 位置 | 说明 |
|---|---|---|---|
| 1 | **批量 JobRequest**：`JobRequest` 支持"build 一次 + run N 段" | `flash/flash_run/remote/job_scripts.py` | `render_job_body()` 增 `runs: Sequence[RunSpecWithWorkdir]`，每个 run 独立 `FL_RUN_DIR_i` + par + 归档子目录；编译段复用（build=None 时跳过） |
| 2 | **批量提交 CLI** | `flash/scenarios/core/submit_cli.py` | `submit sandwich_txn --batch runA:par_a.par runB:par_b.par ...`：多 par 上传、生成 N 个 run 目录声明（JSON 清单随输入上传） |
| 3 | **作业内并行度编排** | `job_scripts.py` | 简单方案: bash 后台 N 个 `srun -n4 ... &` + `wait`（节点内 48 核自管理）；进阶: 按叶块数分组动态调度 |
| 4 | **归档分目录** | `job_layout.archive_outputs()` | 每场景归档到 `flash_output/<scene>/<batch_id>/<run_i>/`，保持现有 patterns 语义 |
| 5 | **批量轮询/哨兵** | `flash/flash_run/remote/slurm_control.py` | `wait_for_job` 已支持单作业；批量场景只需单作业 ID，改造量小 |
| 6 | **资源统计自动落盘（补短板）** | `submit_cli.py` / 新增 `hpc_stats.py` | 作业 COMPLETED 后自动执行 `sacct -j <id> --format=... -P` 并存 `stats.json` 到日志目录 + 下载到本地 runs/<id>/（当前统计散落在笔记，无结构化 manifest） |
| 7 | make_jobs_max 4→16 | scene.json / decl | 编译 91 s → ~25 s（批量作业摊薄后收益小，低优先级） |
| 8 | flash4 单二进制复用 | `BuildSpec` | 同 unit+setup 参数的批量场景共享一个 objdir/二进制（路线 A 前提，改造点 1 天然涵盖） |

改造优先级: **1 → 2 → 4 → 3 → 6**（1+2+4 即可跑通"12 路 × 4 rank"基线；6 随第一轮批量作业一并补上）。

## 4. 实施步骤

1. **验证**（0.5 天）: 路线 B 试验提交（AllocCPUS 是否可 =4）；ntasks=8 扩展性一次实测
2. **MVP 批量作业**（1–2 天）: 改造点 1+2+4；用 4 个变体 par（如不同 lrefine_max / ρ_CH）在 1 个 48 核作业内 4 路并行验证
3. **满载试跑**（0.5 天）: 12 路 × 4 rank，核对 sacct TotalCPU/Elapsed（目标节点利用率 >90%，单场景步速无明显劣化）
4. **统计落盘**（0.5 天）: 改造点 6，形成每作业 `stats.json`
5. **回归**: 跑一次原单场景提交链路，确认无破坏

## 5. 风险与边界

- **共享盘 IO 竞争**: 12 路同时写 chk（每 100 步 ~0.86 MB）→ tmpfs 承接，归档段集中写；极端时 chk 间隔可放宽（100→200 步）
- **AMR 叶块数不足 4 rank 的时段**: 启动初期块少（~16–51 块），rank 空转；批量场景间错峰可忽略
- **同节点 12 进程访存带宽**: 每 rank 单核内存访问极小（64 MiB RSS），预计无瓶颈；试跑时对比单场景步速即可确认
- **超算计费**: 整节点分配下，装满节点不增加费用（同样 48 核 × 时长），纯赚吞吐
- **route A 与 hpc_job 白名单**: `scene.json` 的 `hpc` 节需增批量字段（如 `batch_size`、`run_list`），同步改 `hpc_job._HPC_MANIFEST_FIELDS`
