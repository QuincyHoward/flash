# 01 — SNB 场景报错根因分析与纪律

> 面向 `scenarios/private/SNB/SNB` + 其派生的 `SNBOneCH*` / `SNBOneCH_ml` 场景族。
> 汇总 2026-08 ~ 2026-09 全部已知故障，按**机制分类**而非时间顺序，
> 目的是回答一个问题：**为什么这套东西总是"这样那样报错"？**
>
> 最近更新：2026-09-12（SNBOneCH_ml NC-E 短测收尾）

---

## 0. 一句话结论

**SNB 场景的报错不是随机噪声，而是同一批结构性成因在不同环节的重复显形。**
把它们归并后只有 **5 类**：

| # | 成因类别 | 典型表现 | 占比 |
|---|---|---|---|
| A | **两层结构**（场景层 / 上游树层）职责重叠 | "文件缺失"、"改了不起作用"、"不知道跑的是哪版" | ~35% |
| B | **参数存在三份副本**（模板 par / 部署 par / 运行时 par） | "按 par 判 dtmax 出错"、"tmax 对不上" | ~25% |
| C | **+ug 均匀网格的隐式约束** | 网格对不上、物种丢失、核数不匹配 | ~20% |
| D | **静默失败**（无报错但结果错） | 变量全零、白名单被忽略、收集污染 | ~15% |
| E | **平台差异**（WSL / NC-E / BSCC） | 路径、库、作业脚本、下载超时 | ~5% |

**核心洞察**：A 和 B 都是"**同一份信息有多处存放，且没有单一权威源**"。
C/D 是"**约束没有被前置校验，失败点远离根因**"。
E 是"**同一流程在三个平台上各写一遍**"。

---

## A 类 — 两层结构：场景层与上游树层

### 机制

SNB 不是 FLASH 原生模块，而是**作者实现包 + 场景覆盖**的两层结构：

```
场景层  scenarios/private/tracer/SNB/SNBOneCH_ml/flash_input/
            Config  Makefile  Simulation_*.F90  *.cn4  *.par
            + 9 个 SNB 覆盖 F90

上游树层 FLASHSNB/FLASH4.8/source/Simulation/SimulationMain/SNB_1D_laser/
            （作者参考实现：全部 9 个 F90 + Config + par）
```

部署时**两层合并**到 `SimulationMain/SNBOneCH_ml/`。

### 为什么这会持续报错

1. **场景层"看起来"不完整** → 每次新环境都要靠 `run.sh` 从树里拷；
   树不在（换机器、树被清理）就失败。
2. **改动落在哪一层不明确** → 改了场景层的 F90，但部署脚本的
   拷贝顺序（先场景后树，或反之）决定了到底谁生效。
3. **无法回答"这次跑的是哪版代码"** → 目录里没有权威指纹。

### 实测案例

| 时间 | 现象 | 根因 |
|---|---|---|
| 2026-09-12 | `SNBOneCH_ml/flash_input` 只有 4 个文件（Config/Makefile/Simulation_*），**9 个 SNB 覆盖 F90 全部缺失** | 场景层不自包含，全靠运行时从 `SNB_1D_laser` 拷 |
| 2026-09-12 | `run_flash.sh` 从 `REF_UNIT` 拷 9 个文件，但**未校验目标是否存在** | A 类 + 无前置校验 |
| 2026-09-12 | 树级 physics 补丁（`Diffuse_computeDt.F90`、`hy_uhd_getFaceFlux.F90`）需从 `t001/source_patches` 补 | 树被打包时丢了补丁 |

### 处置（已落地）

- ✅ **补齐 9 个 F90 到 `flash_input/`**，实现场景自包含。
- ✅ 生成 `flash_input/SNB_F90_PROVENANCE.md` 记录**三方哈希**：
  场景层 vs `SNB_1D_laser` vs 已部署单元 —— 本次 **9/9 全一致**。
- ✅ 部署脚本保留"**场景自包含优先 → 树回落**"的双层策略（NC-E `build.sh` 已是此写法）。

### 纪律

> **★ 场景层必须自包含。** 任何"运行时从别处拷"的文件，
> 都要在场景层留一份 + 记哈希，否则不可复现、不可审计。

## B 类 — 参数的三份副本

### 机制

同一个物理参数（`tmax` / `dtmax` / `iProcs`）实际存在**三处**：

| 副本 | 位置 | 谁写 |
|---|---|---|
| ① 模板 par | `flash_input/snbonech_ml.par` | 生成器 |
| ② 部署 par | 远端 `deploy/` 下的同名 par | 上传 |
| ③ **运行时 par** | objdir 内 `flash.par`（被 `sed` 改过） | `run.sh` |

**FLASH 只认 ③。** ①②都只是"看起来的参数"。

### 实测案例（本轮）：

| 参数 | ① 模板 par | ③ 运行时（chk 实测） |
|---|---|---|
| `tmax` | `9.999999999999999e-12` (1e-11) | **`2e-10`** ← `run.sh` 用 `sed` 覆写 |
| `dtmax` | `2.000000000000000e-12` | `2e-12`（未被覆写） |
| `iProcs` | `4` | **`131`** ← `run.sh` 用 `sed` 覆写 |

⇒ 直接读模板 par 会得出**完全错误的结论**。

### 处置

> **★ 判运行时配置，一律读 chk 的 `real runtime parameters` / `real scalars`，不看 par 文本。**
> ```python
> f = h5py.File(frame)
> d = f["real runtime parameters"][()]
> tmax = d["value"][np.char.strip(d["name"]) == b"tmax"]
> ```
> 实测本轮：`tmax = 2e-10`，末帧 `t = 2.000046e-10 s` —— **吻合**。

## C 类 — `+ug` 均匀网格的隐式约束

### 三条铁律

| 铁律 | 内容 | 违反后果 |
|---|---|---|
| C1 | `mpiexec -n` **必须 == par 的 `iProcs`** | 挂死或结果错 |
| C2 | `dx = 域宽 / (iProcs × nxb)`，par 的 `nblockx`/`lrefine*` **被无视** | 改了没效果 |
| C3 | **`dx` 必须 < 最薄层厚度 / 3**（本项目 0.1 µm 层 → `dx ≤ 0.03 µm`） | 薄层物种**从不被写入**（`1e-99`）→ 相邻层直接接触 → **一步即爆** |

### C3 的机制（最隐蔽）

`Simulation_initBlock.F90` 按**单元中心**判据选物种。
若 `dx > 薄层厚度`，**没有任何单元中心落进薄层** → 该物种质量分数恒为 `sim_smallX=1e-99`。

### 核数 ↔ 分辨率对照（本项目，域宽 500 µm）

`nxb = 2^ceil(log2(max(8, 域宽/(0.03µm × nproc))))`

| ntasks | nxb | dx [µm] | 格/0.1µm 层 | 判定 |
|---:|---:|---:|---:|---|
| 4 | 8192 | 0.01526 | 6.55 | ✅ 优 |
| 16 | 2048 | 0.01526 | 6.55 | ✅ 优 |
| 64 | 512 | 0.01526 | 6.55 | ✅ 优 |
| 128 | 256 | 0.01526 | 6.55 | ✅ 优 |
| **131** | 128（硬编码） | **0.02982** | **3.35** | ⚠ 勉强（下限） |
| **192** | 128 | 0.02035 | 4.92 | ✅ 推荐 |
| 256 | 128 | 0.01526 | 6.55 | ✅ 优 |
| 384 | 64 | 0.02035 | 4.92 | ✅ 良 |
| 512 | 64 | 0.01526 | 6.55 | ✅ 优 |

> ⚠ **NC-E `build.sh` 里 `-nxb=128` 是硬编码**，与 131 核的自动档**恰好重合**（巧合）。
> 若核数改成 192，`dx` 会变成 0.02035 µm —— 仍达标，但**不是**自动算法给出 128 的原因。

### 处置

- ✅ `SNBOneCH_ml.py::build_setup_flags_ug()` 已实现按 nproc 反推 nxb，`dx > 0.03 µm` **硬中止**。
- ⚠ **待办**：把 NC-E `build.sh` 的 `-nxb=128` 改为**由 nproc 推导**，消除巧合依赖。
- ★ 验收判据：**chk_0000 里 8 个物种全部 nonzero，每个薄层 ≥ 3 格**。

## D 类 — 静默失败

| # | 现象 | 根因 | 判据 |
|---|---|---|---|
| D1 | 某变量**全零**却不报错 | 该变量是**求解器的 scratch 槽**（如 `QESH` = `Diffuse_solveScalar` 的 `iFactorA`，每次求解前置 0、**从不回写**） | 全树 grep 该 `_VAR` 的**写集**为空 → 属设计，非故障 |
| D2 | `plot_var` 第 13 项起**静默忽略** | `IO/IOMain/Config` 只声明 `plot_var_1..12` | 日志出现 `ignoring unknown parameter` |
| D3 | collect "成功"但本地无数据 | `cp ... 2>/dev/null; rm -f ...` —— 复制失败被吞 | **以本地 chk 帧数 > 0 为成功判据** |
| D4 | 旧 chk 冒充新结果 | 文件名不含 tag 前缀 + `flash_output/` 跨运行累积 | **`sim info` 的 `setup call` + mtime**，绝不用字典序 |
| D5 | HDF5 键查不到 | FLASH 写**小写**键（`qesh`/`cogq`），查 `f['QESH']` 返回 `<absent>` | 先 dump 全部键名 |
| D6 | `t`/`dt` 读成 `nan` 而脚本"像跑通了" | `real scalars` 是 **record array `(name, value)`**，不是 dict-of-arrays | 用 `d["value"][np.char.strip(d["name"])==b"time"]` |
| D7 | 物种"存活计数"恒等于总格数 | 质量分数**下限 `1e-99`** → `v > 0` 恒真 | 改用相对阈值 `v > 1e-6·max(v)` 或空间跨度 |

> **D 类共同点：程序不报错，但结果是错的。**
> 唯一对策 = **对每个关键量建立"应然值"对照**（守恒量、物种数、键数、帧数）。

## E 类 — 平台差异

| 平台 | 特有点 | 已踩的坑 |
|---|---|---|
| **WSL** | `bash -lc` 吞 `$变量`/反引号 | 曾把文件写到 E: 盘根目录；**对策：`.sh` 落盘再 `bash`** |
| **WSL** | h5py 读不了 `\\wsl$\` UNC | 先 `cp` 到 `/mnt/e/...` |
| **NC-E** | SLURM 作业 stdout 被重定向进 objdir | `--output` 文件**永远 0 字节**，别据此判"空转" |
| **NC-E** | 登录环境含 oneAPI | 作业里**禁止 `module purge`** |
| **NC-E** | 结果**不在 objdir** | `run.sh` 结尾移入 `<HOME>/QC/<scene>_deploy/_out/` |
| **NC-E** | `hydra_bstrap_proxy FAILED` | 常是**作业被 kill 后的伴随现象**，非根因 |
| **下载** | SFTP 单连接 ~17 KB/s | 10 MB chk 需 580 s > 默认 120 s 超时 → **每文件独立连接 + 并行** |

## 三条元纪律（从所有案例中提炼）

### ★★★ M1 — 先穷尽比对，再解释

发现"两个文件看起来不同"就下结论是错的。
**先对所有同名文件做 `sha256` 比对**，确定**到底哪些真的不同**。

> 反例：曾据"看起来不同"把某文件当根因，实际两场景该文件**逐字节相同**。

### ★★★ M2 — 单变量对照

排除某变量时**必须做单变量 A/B**。

> 反例：t005 用了 radON 驱动且崩塌 → 曾归因 radON；
> 改回 `none` 仍崩 → 才排除。

### ★★★ M3 — 看实测，不看文本

判运行时配置**一律读 chk / dat 的实测值**。

> 反例：依据 par 文本判 `dtmax`（实际被 `sed` 覆写）；
> 依据 par 文本判 `tmax`（模板 1e-11 vs 实际 2e-10）。

### 辅助启发式

> **若同一现象在多条腿上同步出现 → 根因通常在这些腿共有的路径上。**
> （t005 的 radON/radOFF 崩塌幅度几乎相同 → 与辐射无关。）
