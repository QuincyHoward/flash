| 容器 | 做法 | 实测结果 |
|---|---|---|
| `.docx` | `zipfile` → `word/document.xml`（+ header/footer/footnotes），`</w:p>` 断段、`<w:tab/>`→TAB、`<w:br/>`→换行，去标签 + `html.unescape` | 9 283 字符（SESAME 规格） |

| `.xmind` | `zipfile` → `content.json` 的 topic 树；老版走 `content.xml` 的 `<title>` | 1 724 字符 |

## 3. 三个必须踩过才知道的坑

### 3.1 `.doc` 的文本区**不一定 2 字节对齐**

OLE2 的 Word 文本流可能从**奇偏移**开始。只扫一种对齐会丢掉整段正文。

```python
def _runs_utf16(data, *, align, min_units=5) -> list[str]:
    """按 2 字节单位扫描 UTF-16LE 文本游程（align 为起始偏移）。"""
    ...
cands = {"utf16le@0": _runs_utf16(data, align=0),
         "utf16le@1": _runs_utf16(data, align=1)}
best_key, best_txt = max(cands.items(), key=lambda kv: len(tidy("\n".join(kv[1]))))
```

**两种对齐都扫，取文本更多的一侧**，并把命中的对齐记进 `method`
（实测结果：`ole2-scan(utf16le@0)` 或 `ole2-scan(utf16le@1)`）。

#### 3.1.1 ★ 不能用"奇数字节为 0"判断 ASCII

中文是 BMP 码位（`0x4E00-0x9FFF`），Little-Endian 下是 `\x00\x4e` 这种形态
—— **低字节为 0**。所以"奇数位字节为 0 → 是 UTF-16"这种 ASCII-only 假设
对中文文档**完全失效**。

正确做法是**先把每 2 字节合成一个码位，再分类**：

```python
def _is_text_cp(u: int) -> bool:
    if u in (9, 10, 13):            return True
    if 0x20 <= u <= 0x7E:           return True    # ASCII 可打印
    if 0x00A0 <= u <= 0x024F:       return True    # 拉丁扩展
    if 0x2010 <= u <= 0x203B:       return True    # 通用标点
    if 0x3000 <= u <= 0x303F:       return True    # CJK 标点
    if 0x4E00 <= u <= 0x9FFF:       return True    # CJK 统一表意  ← 关键
    if 0xFF00 <= u <= 0xFFEF:       return True    # 全角
    if 0x0370 <= u <= 0x03FF:       return True    # 希腊字母（物理文档常见）
    return False
```

`test_docsrc.py::test_doc_hyades_ole2_text_extraction` 直接断言
**抽出的中文字符数 > 200** —— 这就是"BMP 码位判定生效"的证据。

### 3.2 `xmind` 的标题是**子元素**不是属性

```xml
<!-- ❌ 错：以为 title 是属性 -->
re.finditer(r'title="([^"]*)"', xml)

<!-- ✅ 对：老版 xmind 的 title 是 <title> 子元素 -->
for tm in re.finditer(r"<title>(.*?)</title>", xml, re.S):
```

初版用属性正则，`Radiation Hydrodynamics.xmind` 抽出 **0 字符**。
改成子元素匹配后抽出 1 724 字符。

### 3.3 `.doc/.xls` 的 8 位游程只作补充

英文 `.doc` 可能用 cp1252 存 8 位文本。所以除了 UTF-16 还要扫 8 位游程，
但**只在 UTF-16 结果稀薄时启用**：

```python
if len(best_txt) < 400:                    # UTF-16 抽得太少 → 试 8 位
    t8 = tidy("\n".join(_runs_cp8(data)))
    if len(t8) > len(best_txt):
        best_txt, r.method = t8, "ole2-scan(cp8/gb18030)"
```

★ 为什么"只作补充"：8 位扫描会把二进制块里的可打印字节也当成文本，
产生大量噪声。只在必要时启用，能显著降低假文本量。

## 4. 「文档 vs 数值数据」闸门

### 4.1 问题

`matter++/ATOMIC/Al.txt` 是 **13.5 MB / 348 636 行的数值表**，
扩展名与 `matter++/Readme.txt`（321 字符的说明）**完全一样**。
只按扩展名扫，会把 13.5 MB 的浮点数当"文档"吞进来。

### 4.2 四道闸门

```python
DOC_SCAN_ROOTS      = (DOC_DIR, MATTER_DIR)   # ★ 刻意不扫整个 MULTI_HOME
DOC_MAX_BYTES       = 12_000_000              # 结构化容器上限
DOC_TXT_MAX_BYTES   =    262_144              # 纯文本候选上限
DOC_NUMERIC_SAMPLE  =        400              # 采样行数
DOC_NUMERIC_RATIO   =        0.5              # payload 行占比阈值
DOC_EXTENSIONLESS   = {readme, manual, …}     # 无扩展名白名单
DOC_ALLOWLIST       = {structure_of_ascii_data_files.txt}  # 数值闸门豁免
```

第 4 道闸门是**内容判别**：

```python
def looks_like_data(path, *, sample=None, ratio=None) -> tuple[bool, float]:
    """判断一个纯文本文件是**数值数据表**还是**说明文档**。

    ★ 为什么需要它：matter++/ATOMIC/Al.txt 是 13.5 MB、34.8 万行的数值表，
    扩展名与 matter++/Readme.txt 完全一样。只看扩展名会把数据当文档吞进来，
    抽出的"文档"就是一堆浮点数。这里用**内容**做第二次判别：
    抽取采样行的非空行，统计 is_payload_line 为真的比例；超过 ratio 即判为数据。
    """
```

实测：

| 文件 | `payload_ratio` | 判定 |
|---|---|---|
| `ATOMIC/Al.txt` | > 0.9 | **数据** → 排除 |
| `matter++/Readme.txt` | 低 | **文档** → 收录 ✅ |

### 4.3 无扩展名白名单

```python
DOC_EXTENSIONLESS = frozenset({
    "readme", "manual", "history", "examples", "modinfo", "install",
    "license", "changes", "changelog", "notes", "info", "release",
})
```

★ `doc/multi1d7.6/` 下的 `README` / `manual` / `history` / `examples`
**没有扩展名**，却是最权威的 `ts` 状态量定义与输入文件规格来源。
`_kind_of(p)` 先试扩展名，无扩展名时查这张白名单：

```python
def _kind_of(p: Path) -> str:
    ext = p.suffix.lower()
    if ext:
        return KIND_BY_EXT.get(ext, "unknown")
    return "text" if p.name.lower() in config.DOC_EXTENSIONLESS else "unknown"
```

### 4.4 数值闸门的**豁免名单**

`doc/Structure_of_ASCII_data_files.txt`（82 字节）的内容**几乎全是数字**：

```
1	0	2	1	12
2	0	1
3	0	4
...
```

`is_payload_line` 会判它为 `True`（数据）→ 被闸门排除。
但它**确实是规格说明**（某种数据结构定义）。

所以设了显式豁免：

```python
DOC_ALLOWLIST = frozenset({"structure_of_ascii_data_files.txt"})
```

★ **豁免是显式的、逐文件列的**，不是"阈值调宽一点"。
调阈值会让真正的数据文件混进来；逐文件豁免只影响那一个文件，
且名单本身在 `config.py` 里可审。这条实测被固化为
`test_allowlist_file_passes_numeric_gate`。

## 5. 输出

```
docs/extracted/
  <原名主干>__<kind>__<sha8>.txt     ← 抽取出的正文（LF，UTF-8）
  MANIFEST.md                        ← 人读清单（4 节）
  manifest.json                      ← 机读（含逐文件 sha256 与抽取方式）
```

文件名规则：

```python
def out_name(self) -> str:
    stem = _UNSAFE.sub("_", self.src.stem).strip("_") or "doc"
    return f"{stem}__{self.kind}__{self.sha256[:8]}.txt"
```

★ **保留原名主干**便于与源文件对照（`Atomic_LEDCOP_不透明度格式说明__ooxml-word__4ed7421a.txt`
一眼看出源是哪个文件）；
**带 sha8** 保证同名不同内容的两个文件不会互相覆盖
（实测 `doc/Hyades 数据格式说明.doc` 与 `matter++/hyades/Hyades 数据格式说明.doc`
就是同名不同内容 → 两个 sha8 后缀）。

### 5.1 `MANIFEST.md` 的四节

| 节 | 内容 |
|---|---|
| 头部 | 扫描根、样本数、成功数、失败数、生成时刻 |
| §1 | 按容器类型计数 |
| §2 | **抽取方式**计数（`zipfile+regex(1 part)`、`ole2-scan(utf16le@0)`、`pdf-zlib(37/37 stream decoded)`…） |
| §3 | 逐文件明细（含 `sha256`、`out_name`、`warnings`） |
| §4 | **告警明细** |

§2 与 §4 是关键：它们让"我是怎么抽的"和"哪一份没抽全"一眼可见。

## 6. 诚实降级：PDF 文本层

### 6.1 CID 字体抽不出来

CID / Type0 字体的码位**不是 Unicode**，`Tj` 里的字节只是字形索引。
从解压流里拿不到真实字符。所以：

```python
if not r.text.strip():
    r.warnings.append(
        "no extractable text layer (CID/Type0 font or scanned image); "
        "cite by page-level metadata only -- do NOT paraphrase unread content"
    )
```

★ **警告文本本身就是纪律**：
`do NOT paraphrase unread content` —— 明确禁止"根据文件名和上下文编一段摘要"。

### 6.2 实测哪些 PDF 抽得出

| PDF | 字符数 | 状态 |
|---|---|---|
| `doc/FEOS/Multi1D++ EOS and Opacity - FEOS程序说明.pdf` | **419 765** | ✅ |
| `FEOS-Package-Documentation2016.pdf` | 102 862 | ✅ |
| `FEOS-Package-Documentation2012.pdf` | 104 114 | ✅ |
| `MPQeos-JWGU-Documentation.pdf` | 47 998 | ✅ |
| `doc/References/1988CPC49(R.Ramis)_MULTI…pdf` | 256 435 | ✅ |
| `doc/gnuplot.pdf` | 629 947 | ✅ |

### 6.3 ⚠️ 风险 R3：抽取伪影必须声明

`FEOS-Package-Documentation2016.pdf` §16.2 的正文受连字/断词伪影影响：

```
"F ormat"  ← 应为 "Format"
"t able"   ← 应为 "table"
```

后果：**无法可靠还原每个字段的语义与数据块列序**。

所以 `feos_native` 解析器**不猜**（见 [20_格式规格与物理量单位手册.md §5.2](20_格式规格与物理量单位手册.md)）：

```python
"""⚠️ 诚实声明（风险 R3）
…
* **完全解码** 行 0 的 10 个字段（有 .301 交叉验证）；
* **定位并解码** rho / T 网格；
* 其余数值按原样存入 raw_values 并标注待定 —— **不猜测列语义**。
"""
```

★ 这是"文档抽取的局限"直接决定"解析器的诚实程度"的完整链条：
PDF 抽不干净 → 字段语义不确定 → 解析器标 `raw_values` + "列序待定"
→ 快照状态 `ok_unverified` → 报告里可查。**不确定性一路传递，不被抹平。**

## 8. 与其它模块的关系

```
docsrc                        （本模块）
  ↓ docs/extracted/*.txt
人工阅读 + 引用 → docs/01..16  （本套文档）
  ↓ 把规格写成代码
registry/declared_types + parsers/*   （族解析器）
  ↓ 把"文档冲突"留痕
identify / audit 报告的 notes 字段
```

★ 闭环一处：**文档里的规格 → 代码里的常量/公式 → 测试里的断言**。
例如 SESAME 规格 docx 里的 `4+2*nr+ne+2*nr*ne` 同时出现在：

```python
# parsers/multi_inverted_eos.py
layout_rule = "F1/with_e0: 4 + 2*nr + ne + 2*nr*ne"

# parsers/base.py
"multi_inverted_eos": lambda nr, nt, ne, ng: 4 + 2 * nr + ne + 2 * nr * ne,

# test_multi_inverted_eos.py
expect_eq(4 + 2 * 66 + 74 + 2 * 66 * 74, 9978)
```

三处一致，且第一处的字符串**就是文档原文**（去掉空格）。
任何人拿到 h5，从 `layout_rule` 属性就能反查到文档里的那一行。
