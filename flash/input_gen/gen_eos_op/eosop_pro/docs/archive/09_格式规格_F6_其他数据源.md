# 09 · 格式规格 F6 · 其他数据源（冷不透明度 / 雨贡纽 / IONMIX / SNOP / 通用曲线）

F6 是**兜底族群**：6 个解析器覆盖 8 类"没有统一前身程序"的数据。
它们合计 **~270 个文件**，是文件数第二多的一群。

| 族名 | 解析器 | 文件数 | 扩展名 | 特征 |
|---|---|---|---|---|
| `coldopacity` | `coldopacity.py` | **67** | `.coldopacity` | **两行自描述表头**（列名 + 逐列单位） |
| `generic_curve` | `generic_curve.py` | **104** | 多种 / 无 | 众数列数兜底，**单位一律 unknown** |
| `feos_aux` | `feos_aux.py` | 60 | `.PAR`/`.cst`/`.mexport`/`.INV` | 参数文件，只做溯源 |
| `snop_input` | `snop_input.py` | 12 | `.SNOP` | Fortran namelist `&daten` |
| `ionmix` | `ionmix.py` | 17 | `.cn4`/`.cnr` | 组分 + 数值区（列序待定） |
| `hugoniot` | `hugoniot.py` | 4 | `.hug` | 列名**与单位**写在 `#` 注释里 |

---

## 1. `coldopacity` —— 全库最直白的单位声明（67 个文件）

### 1.1 实测原文

```
Eph	miu          ← 第 1 行：列名（**制表符**分隔）
eV	cm2/g        ← 第 2 行：**逐列单位**（制表符分隔）
<空行>
10	486606.52638
10.1617	469396.24406
...
```

（源：`matter++/ColdOpacity/Al.coldopacity`）

### 1.2 为什么值得单列一节

这是整个 `matter++` 里**唯一不需要任何推断就能拿到单位**的格式：
列名与单位各占一行、按列对齐、制表符分隔。

```python
def parse_two_line_header(lines) -> tuple[list[str], list[str], int]:
    """解析「列名 / 单位」两行表头，返回 (names, units, payload_start)。"""
```

于是：

```python
table.axis_units["Eph"]  = "eV"        # ← 声明来的，不是猜的
table.field_units["miu"] = "cm2/g"     # ← 同上
table.unit_source = "inline:two-line header (ColdOpacity/Al.coldopacity L0/L1)"
```

### 1.3 另一套写法

`hyades/coldopac.dat` 用**完全不同的**写法：`c` 开头注释 + `z = N` + 点数列。
同一个物理含义（冷不透明度）在库里有两套文本格式 —— 这正是
[11 通用识别协议](11_通用识别协议.md) 要解决的问题。

### 1.4 上游说明（逐字）

> `Coldopac.dat` 离化和原子物理模块在线生成的多群不透明度在低温下可能会产生
> 错误的不透明度，因此提供了**室温的分频不透明度**数据（能点较少）。

所以冷不透明度的用途是**低温修正**，不是主数据源。

## 2. `hugoniot` —— 注释行里的单位（4 个文件）

### 2.1 实测原文

```
# Rho[g/cm^3]  T [eV]         P [Mbar]  E [erg/g]      Us [km/s]      Up [km/s]
2.7059315e+000 2.6771096e-002 1.1245127e-002 3.9018342e+009 4.2385122e+000 ...
```

（源：`matter++/hyades/sesame/eos_41.hug`，157 行）

第 0 行是 `#` 注释 —— 但**列名与单位都在方括号里**，所以它同时是
"注释"和"表头"。解析规则：

```python
_COL_RE = re.compile(r"([A-Za-z][\w/()^.\-]*)\s*(?:\[([^\]]*)\])?")
#                        ↑ 列名                    ↑ 方括号里的单位
```

`payload` 列数由该注释行决定，任何行宽不符 → `CountMismatch`（不静默丢行）。

### 2.2 ★ 第二种写法：括号里带缩放因子

`mat_Al-1.0/Al.feos.hug` 用的是**另一套**写法：

```
Rho [1.000000e+000 g/cm^3]  P [1.000000e+012 dyne/cm^2]  ...
```

括号里第一个数是**该列的缩放倍数**，后面才是单位：

```python
_SCALE_UNIT_RE = re.compile(r"^\s*([-+]?[\d.]+(?:[eE][-+]?\d+)?)\s+(\S.*)$")
#                               ↑ 缩放因子                          ↑ 单位
```

**必须识别**：否则会把 `1.000000e+012 dyne/cm^2` 整串当单位字符串存起来，
而 `P` 的实际数值是 `GPa` 量级却被当成 `dyne/cm²` —— 差 `10¹²` 的静默错误。

处理方式：
1. 用 `_SCALE_UNIT_RE` 拆出 `(scale, unit)`
2. 在 `ParsedTable` 里把 `scale` 记进 `notes`（**不自动乘进去**）
3. `field_units[name] = unit`，并标 `field_units_scaled = scale`

★ **不自动缩放**是有意的：改了数值就破坏了"native 轨逐字保留"的契约。
缩放因子作为**元数据**带给下游，由下游决定怎么用。

## 3. `ionmix` —— 组分解得清，列序不敢猜（17 个文件）

### 3.1 实测原文

```
             21        21            ← L0: 两个整数 = (NR, NT)
  atomic #s of gases:         13    ← L1: 组分原子序数（13 = Al）
  relative fractions:   1.00E+00    ← L2: 各组分相对分数
             30                       ← L3: 一个整数（列数 / 记录类型？）
  0.100000000E+01 0.177828000E+01 ...  ← L4 起为数值区
```

（源：`matter++/Ionmix/al-imx-002.cn4`，11 280 行）

### 3.2 诚实声明（原文）

```python
"""⚠️ 诚实声明
----------
本地 ``matter++`` 内**没有** IONMIX 格式文档；其数据区块的精确列序需对照
LLNL IONMIX 手册。因此本解析器：
* **解码** 组分（Z 列表 + 分数）与 ``(NR, NT)``；
* 把数值区按 **升序单调段** 切出候选网格，其余原样存入 ``raw_values``；
* 标注 *列语义待定* —— 不猜测。
"""
```

### 3.3 已解出的部分

```python
table.axes["rho"]  = [...]      # 由"升序单调段"切出的第一个网格
table.axes["Te"]   = [...]      # 第二个
table.fields["raw_values"] = [...]   # 其余
table.notes += ["组分: Z=[13], 分数=[1.00]", "列语义待定 (无本地 IONMIX 文档)"]
```

**"按升序单调段切候选网格"** 是这里唯一的推断，且它是**结构性**的
（单调性是网格的必要条件），不涉及物理语义 —— 这与阶段 B 的判据同源。

## 4. `snop_input` —— 参数溯源，不是数据表（12 个文件）

### 4.1 实测原文

```
&daten
  NT=20, NR=20, NG=20, NP=3000,
  Z=6.0, RHO1=1.0E-6, RHO2=100.0, T1=1.0E-3, T2=100.0,
  X1=1.0E-3, X2=10.0, EQ=0.0, IGROUP=4, ...
/
```

（源：`mat_C-1.0/C_20G.SNOP`）

`doc/SNOP.MANUAL`（已抽取为 `docs/extracted/SNOP__text__79a5123d.txt`，5 060 字符）
逐字给出了全部参数含义与单位：

| 参数 | 含义 | 单位 |
|---|---|---|
| `NT` / `NR` / `NG` / `NP` | 温度 / 密度 / 群 / 光子能量点数 | — |
| `Z` | 核电荷 | — |
| `RHO1` / `RHO2` | 最低 / 最高密度 | g/cm³ |
| `T1` / `T2` | 最低 / 最高温度 | **keV** |
| `X1` / `X2` | 最低 / 最高光子能量 | **keV** |
| `IGROUP` | 群划分方式（0=用户给，1=linear，2=quadratic，3=log，4=标准 20 群 1eV–5keV，5=灰度 2 群） | — |
| `NPLA` / `NROSS` / `NEPS` / `NZ` | SESAME 表号（Planck / Rosseland / 发射率 / 平均电离度） | — |

`PARAM_UNITS` 字典就是这张表的代码化。

### 4.2 KIND 是 `AUX`，不是 `EOS_TOTAL`

```python
"""它是**参数溯源**文件，不产生 (rho, T) 网格 → KIND 记为 ``AUX``。"""
```

★ 12 个 `snop_input` 文件的用途是回答"**这套 SNP 不透明度是用什么参数算的**"，
而不是提供数值。它们与 [03 注释证据通道](03_注释证据通道.md) 互补：
一个是"文件说了自己是什么"，一个是"文件说了别人是怎么来的"。

## 5. `generic_curve` —— **兜底，同时也是降级**（104 个文件）

### 5.1 覆盖范围

```python
"""适用于 ``matter++`` 里那些「无专门解析器、但明显是列式数值表」的文件，例如
``hyades/ionpot.dat``、``PowerLaws/*.dat``、``XrayMassCoef/*``、``Crystal/*.dat``、
``Thermos/*.ini`` 等。"""
```

### 5.2 策略（保守，不猜测）

```python
"""策略（**保守，不猜测物理语义**）:
1. 剥离注释行（``#`` / ``%`` / ``c`` 开头 / ``REM``）；
2. 统计各行的数值个数，取**众数**作为列数（非众数行 → 记录为异常，不静默丢）；
3. 第 0 列作 x 轴，其余列命名为 ``col1..colN``；
4. 单位一律标 ``unknown``，并把注释原文收集到 ``notes`` 供人工判定。

**绝不因文件名猜测物理量** —— 命名必须来自文档或注释证据。"""
```

### 5.3 ★ 为什么 `generic_curve` 要**单列计数**而不是算成功

审计报告 `by_family` 里 `generic_curve 104` 是可见的（不是混进 `ok` 里），
`01_总览.md` 的"已知边界"里也单列了这条。原因是：

| 维度 | 专门解析器（如 `hyades_eos`） | `generic_curve` |
|---|---|---|
| 轴 | `rho`、`Te`，**带单位与 log10 标记** | `x`，`unknown` |
| 场 | `P`、`E`，**带单位** | `col1..colN`，`unknown` |
| 计数 | 有 `expected` 公式，可验算 | 众数列数，无外部校验 |
| 下游可用性 | 可直接做统一网格插值 | **不可**（没有 `(rho,Te)` 语义） |
| 状态 | `ok` / `ok_unverified` | `ok_unverified`（一律） |

所以 `generic_curve` 的正确读法是"**收下了，但没解出物理含义**"。
它在审计里是**降级**而不是成功 —— 104 这个数字就是当前降级量的**量化指标**。

这也是 [07 §3.1](07_格式规格_F4_FEOS与MPQeos.md) 那个 `hyades` 优先级修复
被重视的原因：修复后 `generic_curve` 从 106 降到 **104** ——
少了 2 个降级，多了 2 个真解。

### 5.4 `.ini` 文件的特殊处置

`Thermos/*.ini`、`ColdOpacity/default.ini` 等文件计数"偏差已在解析时记录"，
所以 `generic_curve` 对它们取 `expected = seen`：

```python
"""``generic_curve`` 对 ``.ini`` 的 ``count_mismatch``：expected = seen
（偏差已在解析时逐条记录，不再重复报 mismatch）。"""
```

原理：`.ini` 是 `key = value` 参数文件，众数列数本身就没有物理意义，
硬套一个 `expected` 公式只会产生假阳性。

## 6. 汇总：F6 的处理哲学

| 数据状况 | 处置 | 状态 |
|---|---|---|
| 有完整单位声明（`coldopacity`、`hugoniot`） | 解出轴 + 场 + 单位 | `ok` |
| 有格式文档（`snop_input`） | 解出参数 + 单位表 | `ok` |
| 有部分结构（`ionmix`） | 解出组分 + 候选网格，其余 `raw_values` | `ok_unverified` |
| 只有列式数值（`generic_curve`） | `x` + `colN`，单位 `unknown` | `ok_unverified` |
| 只有参数（`feos_aux`） | `sections` + `numbers`，不做物理推断 | `ok_unverified` |

★ 一律遵循同一条纪律：

> **宁可标"待定/unknown"，不编一个看起来合理的答案。**

`raw_values`、`colN`、`unit_source="unknown"`、`notes` 里的"列语义待定"——
这些都是**显式的不确定性记账**。它们的数量可以逐周下降（有了文档就升格），
但绝不能靠猜来清零。
