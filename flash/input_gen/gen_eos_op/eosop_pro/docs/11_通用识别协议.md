# 11 · 通用识别协议 —— 给你任意格式的 EOS/op 数据，我怎么识别并提取

> **用户的原始问题**：
> *"你是怎么处理一个任意文本的类型识别和数据提取的？假设我给你任意格式的 eos/op 数据，你怎么识别并提取出来？"*
>
> **本篇就是答案**，而且不是设计文档 —— 是**已经跑在 1214 个真实文件上**的协议。
> 实现在 `eosop_pro/core/inference.py`（434 行）+ `registry/declared_types.py` + `registry/dispatch.py`。

---

## 0. 一句话答案

> **不做「匹配已知格式清单」，而做「结构反演 + 自洽性验证」。**
> 已知格式只是**先验**（用来加速与消歧）；最终一律由**数值证据**定案。

这套立场有个直接的、可验证的后果：
**同一套代码对完全没有先验的文件同样有效** —— 未知格式只是"预算是空的、
纯靠通用模板反演"。

## 1. 完整流程图

```

   ┌──────────────────────────────────────────────────┐

   │             ✅ 网格段严格单调                                 │
   │             ✅ 网格落在物理包络内                             │
   │              → 进候选池                                      │
   └───────────────────────────┬───────────────────────────────────┘

              │ ⑤ 三态判决                             │
              │   存活 1 个 → ok                       │
```

★ 全程**零文本语义依赖**：不读扩展名、不读路径、不读注释、不读伴随文件。

## 2. 五个关键设计决定

### 2.1 决定一：表头/数据的分界**本身就是未知量**

第一版想"按字母找文本头"：

```python
# ❌ 失败的尝试
header_lines = [ln for ln in lines if has_letters(ln)]
```

**实测失败**：F1 / F2 / F4 的表头行是**纯数字**（`37181000 2.7 66 74`），
一个字母都没有。这个办法对它们完全无效。
反过来，payload 行含指数 `E`，所以 naive "含字母" 会把**每一行 payload 都判成表头**。

**修法**：不找分界，**穷举**：

```python
splits = ([res.profile.header_end] if res.profile.header_end > 0
          else [1, 2, 3])          # k = 前导行数
for k in dict.fromkeys(splits):
    header_nums = Σ extract_numbers(nonblank[:k])
    values      = Σ extract_numbers(nonblank[k:])
    ...  # 对每个 k 独立反演
```

然后**在全部自洽解里做唯一性判定**。
—— "只有 k=1 严格自洽" 就是一个**结论**，而不是一个猜测。

### 2.2 决定二：把表头整数当**待解的未知量**

```python
def _dim_candidates(header_nums) -> list[tuple[int, int]]:
    """从表头数值提「维度候选」，**按先验强度排序**。

    实测 F1/F2/F3/F4 的表头都把 NR/NT 放在**最后两位**，
    故「末两个整数」优先；其后是「倒数第 3 与最后」（F3 的 `... rho0 L` 会插入一项）、
    「倒数第 3 与倒数第 2」，最后才是其余组合。
    """
    ints = [int(x) for x in header_nums if x == int(x) and 2 <= int(x) <= DIM_MAX]
    # ★ 必须保留**位置重复值**：NR == NT 的方表（如 `20 20`）一旦去重就没了
    ordered = [(ints[-2], ints[-1])]
    if len(ints) >= 3:
        ordered += [(ints[-3], ints[-1]), (ints[-3], ints[-2])]
    ordered += [(ints[i], ints[j]) for i < j]     # 其余组合兜底
    return dedup_ordered(ordered)
```

三条容易漏的细节：

1. **顺序即先验**。"末两个整数"排第一是实测统计出来的（4 个族都这样），
   不是设计偏好。它让 `ok` 的比例更高（第一候选常命中）。
2. **必须保留重复值**。`AU_SIMPLE_ROSSELAND` 的表头是 `[2401, 4.0, 2.0, 2.0]`
   —— `NR == NT == 2`。如果 `list(set(ints))` 去重，`(2,2)` 就永远找不到。
3. **`DIM_MAX` 上界**（`50000`）必须截断。否则注释里的年份
   `DATED: 22581` 会变成维度候选 `22581`，把候选池炸掉。

### 2.3 决定三：维度可以来自 **payload 开头**，不一定在表头

F3 Hyades 是个反例：

```
行 1: '    41     1.30000000E+01 2.69820000E+01 2.75681460E+00    2004'
行 2: ' 4.40000000E+01 2.20000000E+01 0.00000000E+00 2.75681460E-04 ...'
        ↑ NR=44          ↑ NT=22
```

`NR/NT` 在 **payload 的前两个数**里，不在表头。所以模板支持一个开关：

```python
@dataclass(frozen=True)
class LayoutTemplate:
    name: str
    family: str
    segments: Callable[[int, int, int], tuple[int, ...]]
    dims_in_payload_offset: int | None = None   # ★ F3 用 0
    grid_segments: tuple[int, int] = (0, 1)     # 哪两段是网格

LayoutTemplate("hyades_eos", "hyades_eos", _t_hyades_eos,
               "F3：NR + NT + P + E（NR/NT 在 payload 开头）",
               dims_in_payload_offset=0, grid_segments=(1, 2))
#                                      ↑ 维度自 payload 自解
#                                                        ↑ 网格从第 1 段开始
#                                                          （第 0 段是 NR/NT 两个数）
```

★ 注意 `grid_segments=(1,2)` —— F3 的 segment 0 是 `(2,)`（即 `NR NT` 两个数），
网格从 segment 1 开始。**单调性校验必须跳过 segment 0**，否则会把 `NR/NT`
当成网格去检查单调，产生假阴性。

### 2.4 决定四：容忍度**显式化**，不靠"差不多"

真实文件里有"未声明的额外数值"：多块拼接的分隔数、尾部补零、前导的额外头行数。
所以反演不要求 `avail == sum(segs)`，而是允许：

```python
for lead in range(0, 5):                        # 0..4 个未声明前导值
    for tail in range(0, max(0, min(d1, 8)) + 1):   # 0..min(d1,8) 个尾部值
        avail = len(values) - lead - tail
        if avail == sum(tmpl.segments(d1, d2, ng)):
            → 候选（记录 exact = (lead == 0 and tail == 0)）
```

`tail` 的上界取 `min(d1, 8)` 而不是 `d1`：尾部补零的物理来源是
"凑满一行"（F3 每行 5 字段），所以最多几个；用 `d1`（可能上千）会让搜索空间爆炸。

实测输出（`AL_eos`）：

```
自洽候选 (1):
  - f1_with_e0(d1=66,d2=74,ng=1) payload=9974 mono=True env=True score=2.00
      · 前导表头行数 k=1
  ! k=1: dims=[(66, 74)] values=9974
  ! k=2: dims=[(66, 74)] values=9970
  ! k=3: dims=[(66, 74)] values=9966
```

三行 `!` 就是**容忍度的显式记账**：k=1 严格相等，k=2/3 各差 4 个数
（即"多算了一个表头行"）。**读者能直接看出为什么选 k=1**。

### 2.5 决定五：群数由**剩余预算反解**

F2 多群表的 `ng` 不在任何地方声明。但每子表的规模固定：

```python
per = d1 + d2 + d1 * d2        # 每子表的 rho + T + V
if not per or avail % per:     # 不能整除 → 这个 d1/d2 不对
    continue
ng = avail // per              # ★ 群数 = 剩余预算 / 每子表规模
```

**这是纯计数推断，没有任何猜测。**

★ **实测：这个模板目前对真实的 F2 多群表还不成立。** 见 §8.2 ——
零先验反演 `mat_Au-1.0/AU_op03r` 返回的是 `unrecognized`，
而不是硬凑一个 `ng`。这是一个**诚实的结果**，也是一个**待补模板**的信号。

## 3. 四个校验关卡

| # | 关卡 | 实现 | 不过关的后果 |
|---|---|---|---|
| 1 | **计数守恒** | `avail == sum(segments)` 严格整数相等 | 直接淘汰 |
| 2 | **网格单调** | `_strictly_increasing(seg1)` 且 `_strictly_increasing(seg2)` | 直接淘汰 |
| 3 | **物理包络** | `Envelope.check_values` | 淘汰（但记 `env=False`） |
| 4 | **唯一性** | 候选池大小 | 决定 `ok` / `ambiguous` |

### 3.1 包络的宽容度（避免假阴性）

```python
def _envelope_ok(seg1, seg2, env) -> bool:
    """★ 三种都接受：
    - log10 存储的网格（值域 -8..6）
    - 线性存储的网格（值域 1e-8..1e6）
    - Kelvin 量级（F1 的 T 段；值域 1e2..1e9）
    且**忽略 0**（F1 的 rho[0] == 0 是实测事实，不该因此判失败）。
    """
    cands = sum(1 for lo, hi in (rho_phys, te_eV, rho_log, te_log)
                if _any_in(seg, lo, hi))
    return cands >= 1
```

★ 这一段是**踩过坑的产物**：第一版只接受线性物理量级，
结果真实的 log10 存储文件全部被判 `env=False`，`ok` 数从 6 掉到 0。
修法不是放宽阈值，而是**枚举合法的量纲形态**。

### 3.2 `0` 的特殊处理

`AL_eos` 的 `rho[0] == 0.0`（实测）。包络判定里 0 被**忽略**
（不计入 min/max），但**保留在数据里**。这两件事要同时成立：
- 包络判定忽略它 → 不误判
- 数据保留它 → 不失真

后续统一网格插值时，`0` 会在 `log10` 空间变成 `-inf` → 用
`interpolate.log10_or_nan()` 处理。

## 4. 三态判决：为什么必须有三态

| status | 条件 | 处置 | 为什么不能只有两态 |
|---|---|---|---|
| `ok` | 候选池恰有 **1** 个 | 采用 | — |
| `ambiguous` | 候选池 **≥ 2** 个 | **全部列出**（含 score / 容忍度） | 硬挑一个会静默出错；列全后人工或更强证据能定案 |
| `unrecognized` | 候选池 **0** 个 | 如实报告 + 附行/列剖面 | 编一个"最像的"是**错误**，不是帮助 |

### 4.1 为什么"列全候选"比"挑一个最好的"更对

`ambiguous` 的典型来源是**方表**：`NR == NT` 时 `(ρ,T)` 与 `(T,ρ)` 计数相同。
挑任何一个都可能在另一个上是错的。

```python
res.status = "ambiguous"
# 排序只是**展示**顺序，不是"选一个"
pool.sort(key=lambda t: (-t[1].exact, -t[1].score))
```

排序键只用 `exact`（有无未声明值）与 `score`，**不用"像不像某个已知格式"**
—— 那会引入先验，破坏"证据定案"的立场。

### 4.2 实现在 CLI 上的暴露

```bash
python -m eosop_pro.cli infer <relpath>          # 打印完整反演报告
python -m eosop_pro.cli infer-unknown <relpath>  # 单文件 + 落盘 md
python -m eosop_pro.cli infer-unknown            # 批量：阶段 A 的未决集合
```

`report()` 的输出（实测 `AL_eos`，**零先验**）：

```

行剖面: lines=2495 blank=0 modal_len=60 header=0 payload=2494 header_end=0
列剖面: rows=2494 max_len=60 blank_cols=4 W_gap=15 W_len=15 -> W=15
        （line-length // tokens-per-line，满行语义下精确）

      · 前导表头行数 k=1
```

★ 注意报告里**没有任何语义**：不知道是铝、不知道单位、不知道 `d1` 是 rho。
它只回答"**结构是什么**"。语义必须由声明/注释/文档补上 ——
这就是 [02 两段式执行](02_两段式执行.md) 的分工。

## 5. 从"结构"到"语义"：反演不做什么

反演**只**给结构。以下四件事它**明确不做**：

| 不做 | 为什么 | 谁来做 |
|---|---|---|
| **不判单位** | 单位是**声明**，不是结构（`Al_Z.dat` 与 `Al_Zeff.dat` 结构完全一样） | [03 注释证据通道](03_注释证据通道.md) / [15 单位换算](15_单位换算.md) |
| **不判物理量名** | `d1` 是 `rho` 还是 `T` 还是 `de`？结构上看不出来 | 专门解析器（有文档）+ 注释证据 |
| **不判家族** | 同一个结构可能属于多个族（`f2_gray` 与 `ledcop_split` 计数完全相同） | `identify` 交叉验证 |
| **不给材料身份** | `37181000` 是表号不是材料名 | 注册表 / 伴随文件 |

这是**刻意的边界**：反演的输入被压到"只有字节"，所以它的结论**也与字节同强**。
任何超出字节的结论都必须来自别的证据通道，且**逐条留痕**。

## 6. 失效模式与处置（诚实清单）

| 失效模式 | 症状 | 处置 |
|---|---|---|
| **非文本** | `kind != "text"` | `skipped_non_numeric` + 字节层证据（NUL 位置、编码失败原因） |
| **不是数值表** | payload 行占比 < 阈值 | `unrecognized` + `notes`：`无 payload 行 → 无法反演` |
| **维度超出 `DIM_MAX`** | 所有候选被截断 | `unrecognized`；报告里打印原始表头数值供人工看 |
| **方表歧义** | 候选池 ≥2 且计数相同 | `ambiguous` + **全列**（含 `(d1,d2)` 与 `(d2,d1)` 两侧） |
| **非有限值** | MSVC `-1.#INF0000e+000` | 映射 inf/nan；**标记为上游数据缺陷**、不静默丢 |
| **多块拼接** | 计数 ≈ 整数倍 | `ambiguous`；专门解析器有块检测（`_find_block_starts`） |
| **超大文件** | `ATOMIC/Al.txt` 348 636 行 | 专门解析器用**流式状态机**；反演只对 `max_bytes=4 MB` 以下的文件跑 |
| **PDF 抽不出文本层** | 空文本 | **记 warning**，绝不转述未读内容（见 [17](17_文档抽取.md)） |

★ 最后一条值得强调：`identify` 的 `sweep` 显式设了 `max_bytes = 4_000_000`
（初版不加这个上限时，`identify` 扫全树会超时）。

## 8. 如果给一个**全新**格式的文件，实际会怎样

按协议走一遍：

1. **字节层**：判定 text/binary、编码、NUL。若二进制 → 跳过并记录。
2. **行剖面**：行长众数、payload 占比、前导文本头长度。
3. **列剖面**：字段宽 `W`（或退化为 `len // tokens`）。
4. **反演**：8 个模板 × 维度候选 × k × lead × tail 全搜。
5. **判决**：
   - 若新格式恰好落在某个模板里（计数 + 单调 + 包络全过）→ **`ok`**，
     直接给出 `(d1,d2,ng)` 与分段边界。**这就是"给任意格式也能提取"的实际含义。**
   - 若结构超出 8 个模板的表达力 → **`unrecognized`**，
     输出完整剖面报告。此时**正确的下一步是补一个模板**，不是硬猜。

### 8.1 实战案例 A：`AL_eos` —— 模板命中，`ok`

```
状态: ok
自洽候选 (1):
  - f1_with_e0(d1=66,d2=74,ng=1) payload=9974 mono=True env=True score=2.00
```

零先验、唯一解、结构完全正确。这就是"能提取"。

### 8.2 实战案例 B：`AU_op03r`（F2 多群）—— 模板**不**命中，`unrecognized`

```
$ python -m eosop_pro.cli infer mat_Au-1.0/AU_op03r
=== 通用布局反演报告 ===

行剖面: lines=2240 blank=0 modal_len=60 header=2 payload=2200 header_end=2
列剖面: rows=2200 max_len=60 blank_cols=0 W_gap=None W_len=15 -> W=15
  · 未发现可用的空白列 → 字段紧邻（负号吃掉前导空格的典型情形），
    只能依赖长度法 —— 这也是 matter++ 的常态
表头数值: []
维度候选: []
payload 数值个数: 0
自洽候选 (0):
  ! k=2: dims=[(20, 10), (20, 20)] values=8895
  ! k=3: dims=[(20, 10), (20, 20)] values=8891
  ! 所有 (分界 × 维度 × 模板) 组合都不满足计数守恒
```

**这个 `unrecognized` 是正确的、有价值的输出**，理由有三条：

1. **它没说错**。凑一个 `(20,20,ng=20)` 出来能让计数"看起来对"，
   但真实的 F2 多群布局里，每个子表还夹着**一行频率边界**
   （`[freq_lo] [freq_hi]`，见 [20_格式规格与物理量单位手册.md §3.1](20_格式规格与物理量单位手册.md)），
   而 `_t_f2_mg` 的扁平公式没建这个模。硬凑出来的解会在
   "哪个数是边界、哪些是数据"上**静默错位**。
2. **它给出了诊断**。`values=8895` 与 `W=15`、`header=2`、
   `dims=[(20,10),(20,20)]` 全都打印出来了 —— 补模板的人**不需要重新跑一遍探测**。
3. **它与阶段 A 的结论一致**。专门解析器（`multi_opacity`）对这 391 个文件
   解出的 `actual == expected`，说明**内容是对的**；反演只是"模板不够细"。
   两者并存恰好证明了"声明通道"与"内容通道"的分工。

**这就是"给任意格式"的诚实边界**：能建模的格式一定解得出；
建不了模的格式**明说解不出**，并把补模板需要的全部信息摆出来。

### 8.3 补一个模板的成本

```python
def _t_my_new_format(d1, d2, ng):
    return (d1, d2, d1 * d2, ...)          # 照抄一次计数公式

TEMPLATES += (LayoutTemplate("my_new_format", "my_family",
                             _t_my_new_format, "说明",
                             dims_in_payload_offset=None,
                             grid_segments=(0, 1)),)
```

★ **一个函数 + 一行注册**。这就是把"结构知识"与"字节处理"彻底解耦的收益：
`lineprofile` / `columnprofile` / `byteclass` / `fortran_numbers` 一行都不用改。

（F2 多群模板的补法：需要给 `LayoutTemplate` 增加"每子表附加 `nb` 个边界数"
的参数，或让 `segments` 返回带重复单元的结构。这是已知的下一步工作。）

## 9. 一句话总结

> 我识别任意格式的方式不是"认得它"，而是"**用计数守恒、单调性和物理包络把它逼到只能有一种结构解释**"。
> 逼不出来就如实说 `unrecognized` 并把剖面摆给你看；
> 有多个解释就**全部列出来**而不是挑一个；
> 语义（单位、物理量名、材料）一律另走证据通道，且逐条留痕。
