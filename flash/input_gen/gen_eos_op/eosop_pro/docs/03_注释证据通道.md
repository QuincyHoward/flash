# 03 · 注释证据通道

> **用户的要求**：*"文件类型识别的时候可以利用那些注释或者文字说明。"*
>
> 本篇把"注释/文字说明"从**口头约定**变成**可编程的证据源**：
> 它有自己的索引、自己的优先级、自己的仲裁记录，且最终写进 HDF5 与报告。

---

## 1. 为什么注释是"第一等级"证据

`matter++` 的单位约定是**三十年演化**出来的，同一物理量在不同族里单位不同。
最典型的例子（原文摘自 `docs/extracted/MULTI使用的SESAME数据文件格式__ooxml-word__3e289d7f.txt`）：

> **Zeff**
> 温度和密度采用对数坐标系，Zeff也采用了对数坐标系。温度单位是 **keV**,
> 密度单位是 g/cm3.（**与不透明度不同，不透明度温度单位为 eV**）
>
> 注：之前的Multi计算中一直发现电离度偏高，况龙钰(20160109)发现是**温度的单位弄错了**，
> SNOP等输出的SESAME数据，温度的单位一直是 **keV**。但是在Multi的输入是按照
> **eV** 输入的，因此导致电离度明显偏高。
>
> 因为之前(20160109)的计算中按照 eV 输入，因此在创建 Thermos 的数据文件时
> 电离度也是按照 eV 创建的，不存在偏大的情况。但程序自 20160109 之后，
> 统一将输入按照 keV 执行；相应的 Thermos 文件夹中所有的电离度文件
> (名字为 `X_Z.dat`) 温度按照 keV 重新生成，以使其格式与 SNOP 等 SESAME 格式一致。
> **名字为 `X_Zeff.dat`(温度单位为 keV)，以与之前的 `X_Z.dat`(温度单位为 eV) 相区分。**
> Material.base 中替换所有 `X_Z.dat` 为 `X_Zeff.dat`。

这段文字里包含的信息**无法从数据反推**：

1. 不透明度族 T 用 eV，Z̄ 族 T 用 keV —— 差 10³。
2. 历史上曾经混用，**同名文件有两种单位**。
3. 区分方式就是**文件名后缀** `_Z` vs `_Zeff`。
4. 上游已经用 `material.base` 做了替换。

没有这段说明，任何"从数据猜单位"的方法都会在 `Al_Z.dat` 与
`Al_Zeff.dat` 之间摇摆 —— 因为两者数据形态完全一样，只差一个常数因子。

**结论**：注释/说明不是"补充材料"，而是**唯一的单位权威**。所以它必须是
一等公民的证据通道。

## 2. 四类注释源

| 类别 | 形态 | 实例（实测） | 解析器 |
|---|---|---|---|
| **伴随文件** | 独立文件，基名相同或带固定后缀 | `AU_info`、`Al.inhalt`、`Al.readme`、`mat_Ba/Readme.txt` | `registry/annotation_store.py` |
| **前缀注释文件** | 以 `#` 开头的文件 | `#xxx` | 同上 |
| **内联声明** | 数据文件**头部**的文字行 | `Opacities in cm**2/gm, T in keV, density in gm/cc` | `core/annotations.py` |
| **注册表** | 结构化声明 | `material.base` 的 `ZEFF mat_X-1.0 X_Zeff` | `registry/material_base.py` |

### 2.1 伴随文件的识别规则

```python
# config.py
ANNOTATION_SUFFIXES = (".info", ".inhalt", ".readme")
ANNOTATION_NAMES    = frozenset({"readme", "readme.txt", "modinfo"})
ANNOTATION_PREFIXES = ("#",)
```

★ 三个实测踩到的坑：

1. **`AU_info` 用的是下划线不是点。** 最初只匹配 `*.info`，
   结果 Al/Au 的单位声明全丢，全部退化成 `ok_unverified`。
   修法：把 `_info` / `_inhalt` / `_readme` 一律当伴随文件。
2. **`Readme.txt` 是 GB18030 中文**，不是 UTF-8。编码链要包含 `gb18030`。
3. **CJK 边界不能用 `\b`。** Python 的 `\b` 在"汉字 ↔ 拉丁字母"之间
   **不产生边界**，所以 `_file_unit_hints_from_text` 里若用 `\bkeV\b`，
   形如 `温度单位是keV` 的句子会匹配失败。修法：改用自定义的
   "非字母数字"边界断言。

### 2.2 `AnnotationStore` 结构

```python
class AnnotationStore:
    companions: dict[str, list[CompanionFile]]   # 基名 → 伴随文件
    def for_file(self, relpath) -> list[Annotation]
    def merged_units(self, relpath) -> dict[str, str]     # 该文件所有单位声明合并
    def unit_hint_for(self, relpath) -> str | None        # 文件名模式提示
    def table_id_kinds(self, relpath) -> dict[int, str]   # SESAME id → 类型
    def build(self) -> "AnnotationStore"                  # 幂等，可重复调用
```

`build()` 扫一遍 `matter++`，把伴随文件全部读入、解析、建索引。
实测伴随注释文件数量随材料而变（`audit` 报告里逐次打印）。

## 3. 单位仲裁：四级优先级

`registry/units_registry.py` 定义了**唯一**的仲裁链：

| 优先级 | `unit_source` 取值 | 来源 | 可信度 |
|---|---|---|---|
| 1 | `companion` | 伴随文件里的显式单位表 | 最高 |
| 2 | `inline` | 数据文件头部内联声明 | 高 |
| 3 | `envelope` | **物理包络反演**（数据本身落在哪个量级） | 中（推出来的） |
| 4 | `config_default` | 族默认值（`config.py` / 解析器常量） | 低（兜底） |

```python
def adjudicate(relpath, field, *, declared_value=None, envelope_value=None,
               family_default=None) -> tuple[str, str]:
    """返回 (unit, source)。source ∈ {companion, inline, envelope, config_default}"""
```

**关键**：`envelope` 排在第 3 位而不是第 1 位。理由是包络反演只能给出量级，
而注释能给出**确定性**结论。当二者冲突时，**注释赢**，但冲突会记 warning
（见 §5）。

### 3.1 包络反演怎么做（以及它为什么会错）

```python
# config.py
LOG_T_EV_IF_GE  = 4.5   # log10(T) >= 4.5 → 一定是 eV 量级
LOG_T_KEV_IF_LE = 2.5   # log10(T) <= 2.5 → 一定是 keV 量级
```

实测这两组**无重叠**：eV 网格的 `log10(T)` 落在 `[0, 6]`，
keV 网格落在 `[-3, 3]`。判据是"落在哪个区间"，中间带 `(2.5, 4.5)` 判为不可判。

★ 但包络有**两个致命盲区**，所以不配当第一权威：

1. **只差一个常数因子的两个文件，包络一样。** `Al_Z.dat`（eV）与
   `Al_Zeff.dat`（keV）的 `log10` 值恰好差 3，都落在 `[0,6]` 内 ——
   包络判不出谁是谁。注释里的 `_Z` / `_Zeff` 命名约定才是判决依据。
2. **低 T 端越界。** 若某个 eV 网格的低端是 `1e-2 eV`（`log10=-2`），
   它落在 keV 区间里，包络会误判。所以判据必须是**整个网格的趋势**
   （中位数或 `log10(max)`），不是单点。

## 4. 内联声明的抽取

`core/annotations.py::extract_from_text()` 从数据文件的头部文字里抽七类信息：

| 字段 | 锚点模式（`core/anchors.py`） | 例 |
|---|---|---|
| `material` | `TOPS results for <X>`、材料名行 | `LiH` |
| `provenance` | `LANL SESAME #2700-304 DATED: 81678` | SESAME 表号 + 日期 |
| `dims` | `Number of T = 69  Number of rho = 50` | `{T: 69, rho: 50, NG: ...}` |
| `units` | `Opacities in cm**2/gm, T in keV, density in gm/cc` | `{kappa: cm2/g, Te: keV, rho: g/cc}` |
| `table_ids` | `xxxx3nnn` SESAME 风格 8 位号 | `[27003003, ...]` |
| `group_scheme` | `IGROUP = 4`、`standard division with 20 groups` | `{IGROUP: 4, NG: 20}` |
| `powerlaw` | `Rosseland opacity (cm): 6.0e-06 * T^1.0 / rho^1.0` | `{power: 1.0, c: 6e-6}` |

锚点库（`core/anchors.py`）是一个 **42 条**模式的字典 `ANCHORS`，
每条都至少有一个真实样本行写在 docstring 或测试里：

```python
ANCHORS: dict[str, re.Pattern[str]] = {
    "ledcop_n_t":     _c(r"Number\s+of\s+T\s*=\s*(\d+)"),
    "ledcop_units":   _c(r"Opacities\s+in\s+cm\*\*2/gm,\s*T\s+in\s+(\w+),"
                         r"\s*density\s+in\s+(\S+)"),
    "ledcop_source":  _c(r"(TOPS|Ledcop|LEDCOP)\s+results\s+for\s+(\S+)\s+on\s+(.+)"),
    "sesame_number":  _c(r"\b(\d{4})([2-5])(\d{3})\b"),      # xxxx{2,3,4,5}nnn
    "snop_table_id":  _c(r"NPLA\s*=\s*(\d+)"),
    "snop_groups_de": _c(r"FG\(1\)\s*=\s*([\d\.,\s]+)"),
    "powerlaw_units": _c(r"Rosseland opacity \(cm\):\s*([\d\.eE+-]+)\s*\*\s*"
                         r"T\^([\d\.+-]+)\s*/\s*rho\^([\d\.+-]+)"),
    ...
}
```

42 条按族分布（`_c` 是 `re.compile` 的薄封装，只为了在字典里少写一个函数名）：

| 前缀 | 条数 | 覆盖 |
|---|---|---|
| `ledcop_*` | 11 | F5 LEDCOP/ATOMIC 的维度、单位、来源、成分、温度/密度网格头、多群块 |
| `info_*` | 15 | 伴随 `*_info` 文件的表号映射（`IR`/`IP`/`IE`/`IMI`/`IME`…）与原子量 |
| `powerlaw_*` | 5 | 幂律不透明度拟合的系数、指数、适用区间 |
| `snop_*` | 5 | SNOP namelist 输入（`NPLA`/`NROSS`/`NEPS`/`NZ`/`FG`） |
| `sesame_*` / `qeos_*` / `dated` | 3 | 溯源行 `LANL SESAME #2700-304 DATED: 81678` |
| `material_*` | 2 | `material.base` 块头与键值 |
| 其它 | 1 | `units_eV_keV`、`coldopacity_note` |

### 4.1 SESAME 类型位：`s[-4]` 而不是 `s[3]`

SESAME 表号 `xxxx{2,3,4,5}nnn` 的**类型位是右起第 4 位**
（`registry/database_index.py`）：

```python
SESAME_DIGIT_KIND = {"2": "ZEFF", "3": "PLANCK", "4": "ROSSELAND", "5": "EMISSIVITY"}

def sesame_digit_of(table_id: int | str) -> str:
    s = str(table_id)
    return s[-4]          # ★ 不是 s[3] / s[-1]
```

实测对照：

| 表号 | `s[-4]` | `s[3]` | 正确含义 |
|---|---|---|---|
| `20202000` | `2` | `0` | 2 = 平均电离度 Z̄ ✅ |
| `27003003` | `3` | `0` | 3 = Planck ✅ |
| `27004003` | `4` | `0` | 4 = Rosseland ✅ |
| `27005003` | `5` | `0` | 5 = 发射率 ✅ |

用 `s[3]` 会把所有表的类型都读成 `0`（材料号第 4 位），全盘错位。

### 4.2 标签归一化

上游写法不统一，必须先归一。`parsers/multi_opacity.py` 里：

```python
def norm_label(name: str) -> str:
    """ROSSELAND / rosseland / ROSS  →  ROSSELAND"""
```

★ 最初 `LABEL_RE` 只覆盖了缩写 `ROSS`，**漏掉完整拼写 `ROSSELAND`**，
导致 F2 里用全拼标签的表无法归类。修法：新增完整拼写模式 + `norm_label()` 归一。

`registry/annotation_store.py` 里还有一张"伴随文件键 → KIND"映射表，
覆盖三套不同写法：

```python
{"Z": "ZEFF", "P": "PLANCK", "R": "ROSSELAND", "E": "EMISSIVITY",
 "IP": "PLANCK", "IR": "ROSSELAND", "IEPS": "EMISSIVITY",
 "NPLA": "PLANCK", "NROSS": "ROSSELAND", "NEPS": "EMISSIVITY", "NZ": "ZEFF"}
```

`AU_info` 里的 `Z:27002003; P:27003003; R:27004003; E:27005003`
就是通过这张表变成 `{27002003: "ZEFF", 27003003: "PLANCK", ...}`，
成为**最高优先级**的表号→类型证据（优于按数字位推断）。

## 5. 冲突的记录方式

仲裁链**不隐藏**冲突。当 `companion` 与 `envelope` 结论不一致时：

```python
snap.note(f"⚠️ 单位冲突：伴随文件声明 {decl}，数据包络指向 {env}；"
          f"按优先级采用 {decl}（companion > envelope）")
```

这条 warning 会：
1. 进 `ParseSnapshot.diagnostics`
2. 进 `audit_all.*.md` 的"§8 成功但有告警的文件"清单
3. 进 HDF5 的 `/meta/warnings`

实测 `Al_Zeff.dat` vs `Al_Z.dat` 的裁决过程（`Δlog10 = 3.000`）：

| 文件 | 声明（companion/name） | 包络 | 仲裁结果 |
|---|---|---|---|
| `Thermos/mat_Al/Al_Zeff.dat` | `keV`（`_Zeff` 命名约定） | 不可判（区间重叠） | **keV** |
| `Thermos/mat_Al/Al_Z.dat` | `eV`（`_Z` 命名约定） | 不可判 | **eV** |

两者都判成功，`unit_source = companion`，无冲突。这正是"注释优先"的价值：
**包络本来判不出来，是注释救的场。**

## 6. 一个真实的"注释救场"链

`AL_eos.feos`（见 [02](02_两段式执行.md) §4）是"声明错、内容纠正"的例子；
反过来也有"声明对、内容看不出"的例子：

**F1 反演 EOS 的 `T` 单位是 Kelvin**（原文出处：
`docs/extracted/MULTI使用的SESAME数据文件格式__ooxml-word__3e289d7f.txt`）：

> 参数单位制分别为(cgs)
> `r[nr]` 密度(g/cc)
> `de[ne]` 能量(能量列表，与冷能量的差距, 单位 **Mbar*cm3/g**)
> `e0[nr]` 冷能量(密度对应的冷能量列表，单位 Mbar*cm3/g)
> `P[ne*nr]` … 单位为 **Mbar**
> `T[ne*nr]` 密度为 r[0~nr-1]，能量为 de[i]+e0[0~nr-1] 时的温度（**Kelvin**）

如果只看数据，`T` 段的量级（`1e4` 量级）在 eV 与 K 下都"看起来合理"
（`1e4 K ≈ 0.86 eV`，而 `1e4 eV` 是 1 万 eV）。**只有注释能定案。**
`config.EV_PER_K = 8.617333262e-5` 就是这条注释的代码化。

## 8. 新增一个注释源要改哪里

1. 在 `core/anchors.py` 加模式（**必须附一个真实样本行**在 docstring 里）
2. 在 `core/annotations.py::extract_from_text()` 接上字段
3. 在 `config.py` 加文件后缀/名前缀（若是伴随文件）
4. 在 `registry/annotation_store.py` 索引它
5. 在 `test_anchors.py` + `test_annotations.py` 各加一条命中与一条**不命中**测试
6. 重跑 `03_audit.bat`，确认 `ok` 数上升、`ok_unverified` 数下降

第 6 步是关键：**注释通道的成效用 `ok` 与 `ok_unverified` 的此消彼长来量化**，
不是靠感觉。
