## 0. 阅读须知

### 0.1 ⚠️ 溯源纪律（本手册最重要的一条）

**单位与物理量的权威来源，必须是「外部权威文档」或「数据文件自身的声明」——
不得是本项目自己的解析器。**

原因：解析器是**依据权威文档编写**的。若溯源指向解析器，
就形成 `解析器 ← 溯源文档 ← 解析器` 的**循环论证**，等于没有溯源。

因此本手册对每一族都给出**两个独立字段**：

| 字段 | 含义 | 形式 |
|---|---|---|
| **溯源文档** | 判定该单位/结构的**外部依据** | 本地文件路径 + 章节/行号 |
| **实现脚本** | 编码该判定的 Python 模块 | `eosop_pro/parsers/<x>.py` |

**溯源优先级**（高 → 低）：

| 等级 | 记号 | 含义 | 例子 |
|---|---|---|---|
| **L1** | `format:` | **写出该格式的程序源码**或**官方程序手册** | `abjt_03.f` L4683；`Hyades 数据格式说明.doc` |
| **L2** | `declared:` | **数据文件自身内嵌**的单位声明 | `.coldopacity` 第 2 行；`ATOMIC/*.txt` 的 `T in keV` 行 |
| **L3** | `default:` | 程序约定默认值（文件未声明时采用，**须注明**） | F2 未声明时回退 `eV` |
| **L4** | `inferred` | 由**量纲/赋值表达式**反推（须附推导式） | `.cn4` 的 `p_ion` = `cm^-3·eV·J/eV` |
| **L5** | `unknown` | **无任何本地依据 → 标 unknown，不使用、不猜测** | `.cn4` 的 `deion_dn`（源码自注 `not sure`） |

> ⚠️ 解析器的 `ParsedTable.unit_source` 字段**记录的是等级与依据**，
> 它是**实现细节的登记处**，**不是**溯源本身。本手册的"溯源文档"列才是一手依据。

### 0.3 ⚠️ 三条跨族铁律

1. **同一物理量在不同族单位不同** —— `T` 在 F1/F3/F4/F6 是 `eV`，
   **在 F5 LEDCOP 是 `keV`**（差 1000 倍）。
2. **F6 IONMIX 的密度轴是数密度 `cm^-3`**，其余族均为质量密度 `g/cm3`。
3. **F6 IONMIX 的 P/E 是 SI 派生的 `J/cm3` / `J/g`**（**不是** `Mbar` / `erg/g`）。

## 2. F1 —— MULTI 反演 EOS

**溯源文档**: `MULTI使用的SESAME数据文件格式.docx`（抽取文本见 §0.2）
**实现脚本**: `eosop_pro/parsers/multi_inverted_eos.py`

### 2.1 结构规格（实测）

每个**块**以一行 4 数表头开始：

```
table_id   rho0(未用)   nr   ne
```

其后为 payload（T-major，rho 快变，索引 = `i_de*nr + j_rho`）。

★ **两种 payload 布局并存**（实测，由**计数守恒唯一确定**）:

| 布局 | 数组 | 实测文件 |
|---|---|---|
| `with_e0`（含冷能） | `rho(nr) de(ne) e0(nr) P(nr·ne) T(nr·ne)` | `AL_eos` → 9978 |
| `no_e0`（无冷能） | `rho(nr) de(ne) P(nr·ne) T(nr·ne)` | `AU_eosd` → 4770 |

计数公式: `with_e0` → `4 + 2·nr + ne + 2·nr·ne`；`no_e0` → `4 + nr + ne + 2·nr·ne`。
两者只差一个 `nr`，**必须用实测计数反解**，不能假定。

**实测基准**:

| 文件 | 表头 | 解出计数 |
|---|---|---|
| `mat_Al-1.0/AL_eos` | `37181000 2.7 66 74` | **9978** = 4+132+74+9768 ✓ |
| `mat_Au-1.0/AU_eos` | `27001000 19.300003 101 23` | — |
| `mat_Be-1.0/BE_eos` | `2020 0.0 101 50` | — |

## 3. F2 —— MULTI 不透明度 / Zeff / NLTE / EPS ★最大族

**溯源文档**:
* `MULTI使用的SESAME数据文件格式.docx`（表结构）
* `matter++/Thermos/Readme.txt`（**温度单位声明的权威来源**）
* `matter++/ATOMIC/*.txt` 的内嵌单位行（L2）

**实现脚本**: `eosop_pro/parsers/multi_opacity.py`

### 3.1 结构规格（实测，推翻"单一扁平表"假设）

**多群文件是 `ng` 个独立子表的串联，每个子表自带完整表头**：

```
[子表头1] [能群边界线] [rho 网格] [T 网格] [值]
[子表头2] [能群边界线] [rho 网格] [T 网格] [值]
...
```

行数算术精确验证（**最硬的证据**）:

| 文件 | 算术 | 结果 |
|---|---|---|
| `AU_op03p` | 20 子表 × (1 头 + 1 边界 + 110 payload) | = 2240 ✓ |
| `Thermos/Al_Planck.dat` | 25 子表 × (1 + 1 + 127) | = 3225 ✓ |
| `AU_SIMPLE_PLANCK_MG` | 24 子表 × (1 + 1 + 2) | = 96 ✓ |

子表头之间是**逐群变化的光子能量区间**（`1.0 10.0` → `10.0 50.0` → `50.0 75.0` …），
故"行 2 的光子能量标记"实为该群的 `(E_lo, E_hi)`。

`opbe` 更复杂：是**不同 KIND 的表**串联（`opbe.inhalt` 声明 4 个表号
`NPLA/NROSS/NEPS/NZ`）→ 由 `parse_all` 拆成多张表。

**行 1 的 `<f2>` 是类型枚举，不是 Zbar**（实测于 547 个 F2-like 文件）：

| `f2` 值 | 含义 |
|---|---|
| 0 | EOS / 理想气体类 |
| 1 | 出现 34 次，含义待定（风险 R2） |

### 3.2 物理量与单位

| 量 | 单位 | 等级 | **溯源文档** | 实现脚本 |
|---|---|---|---|---|
| `rho`（密度轴） | `g/cm3` | L1 `format:` | `MULTI使用的SESAME数据文件格式.docx` | `multi_opacity.py:342` |
| `Te`（温度轴） | `eV` | **L2/L3** | **文件内嵌声明**（如 `ATOMIC/*.txt` 的 `T in keV` 行）→ `declared:`；未声明时 `default:eV` | 同上 `:345` |
| `kappa_*`（不透明度） | `cm2/g` | L1 | `MULTI使用的SESAME数据文件格式.docx` | 同上 `:361` |
| 非 `kappa` 字段（Zeff 等） | `-`（无量纲） | L1 | 同上（Z̄ = n_e/n_tot 为比值） | 同上 `:361` |

### 3.3 ⚠️ ZEFF 表 eV/keV 双套陷阱（**本项目第二易错处**）

ZEFF 表存在 **eV / keV 两套**，**纯数字无法区分**。实测反例：

```
matter++/Thermos/mat_Al/Al_Zeff.dat    → keV
matter++/Thermos/mat_Al/Al_Z.dat       → eV
```

两者**表头与行数完全相同**（均 128 行），`logT` 区间只差 `log10(1000) = 3.000`。

**权威区分依据 = `matter++/Thermos/Readme.txt`**（L2 `companion`）：
该文件按**文件名模式**声明 `*_Z.dat` = eV、`*_Zeff.dat` = keV。

**四级裁决链**（实现于 `registry/units_registry.py`，优先级高 → 低）：

1. `companion` —— 伴随注释文件的**文件名模式**声明（如 `Thermos/Readme.txt`）
2. `inline` —— 文件内嵌单位声明（`ATOMIC/*.txt`、`.coldopacity` 两行表头）
3. `envelope` —— 兜底启发式：由 logT 上限判断（`≥4.5 → eV`；`≤2.5 → keV`），
   并用物理包络 `T ∈ [1e-2, 1e6] eV` 复核
4. `config_default` —— 格式默认（F2 默认 eV）

> 实现脚本 `multi_opacity.py:378,380`：未声明时回退 `default:eV` 并在 `unit_source`
> 中**显式标注**。裁决记录写入 h5 的 `/meta/units`，`source` + `evidence` 可追溯。

## 5. F4 —— FEOS / MPQeos

**溯源文档**:
* `MPQeos-JWGU-Documentation.pdf`（MPQeos 模型与单位）
* `FEOS-Package-Documentation2012.pdf` / `2016.pdf`（FEOS 包与 `.feos` 头部）
* `Multi1D++ EOS and Opacity - FEOS程序说明.pdf`（**`.301/.304/.305` 的换算说明**）

**实现脚本**: `eosop_pro/parsers/mpqeos.py`、`feos_native.py`、`feos_tabdata.py`、`feos_aux.py`

### 5.1 `mpqeos`（`.301` / `.304` / `.305`）

结构: 行 1 = `Id  Density  NR  NT`；payload = `[R(NR)] [T(NT)] [P] [E] [Z]`。
**计数守恒**: `4 + NR + NT + 3·NR·NT`

★ 两个实测陷阱:
1. **表头不可定宽切分**：ID 字段宽 16 或 17 列**不定**，固定切分会产生污染字段
   （如 `'2.70000000e+00 1'`）。表头全为空格分隔正数，故交给 **L2 正则**；
   payload 才用**逐文件推断**的定宽 `W = len(line)/4`。
2. **字段宽逐文件不同**：`mat_Al-1.0/FEOS/Al.feos.301` payload 行 60 字符（`W=15`），
   而 `mat_He/Untitled.304` 是 64 字符（`W=16`）。

实测基准: `Al.feos.301` 头 `37170301 2.7 192 69` → 192+69+3·192·69 = **40005** ✓

| 量 | 文件内单位 | 单位 | 等级 | **溯源文档** | 实现脚本 |
|---|---|---|---|---|---|
| `rho`（密度轴） | — | `g/cm3` | L1 | `MPQeos-JWGU-Documentation.pdf` | `mpqeos.py:108` |
| `Te`（温度轴） | Kelvin | `eV` | L1 | 同上 | 同上 `:111` |
| `P`（压力） | GPa | `Mbar` | L1 | `Multi1D++ EOS and Opacity - FEOS程序说明.pdf`（明写 `1 GPa = 1e-2 Mbar`） | 同上 `:117` |
| `E`（比内能） | MJ/kg | `Mbar*cm3/g` | L1 | 同上（明写 `1 MJ/kg = 1e-2 Mbar·cm³/g`） | 同上 `:122` |
| `Z`（平均电离度） | — | `-`（无量纲） | L1 | `MPQeos-JWGU-Documentation.pdf` | 同上 `:127` |

> `SESAME` 库用 压强 GPa / 能量 MJ/kg / 密度 g/cc / 温度 Kelvin；

```

量纲逐步展开:

```

   ↑         ↑         ↑

其中 `1.602E-19` 即元电荷 `1.602176634e-19 J/eV` 的 Fortran 简写
（理想气体律 `P = n k_B T` 在 eV–J 单位制下的 `k_B`）。

### 7.5 `densnn` 是**数密度**，不是质量密度（§5.1 权威）

`IONMIX用户指南.md:735`（§5.1 输出量表）明写:

| 输出量 | 单位 | 物理意义 |
|---|---|---|
| Number density | `cm^-3` | **核子数密度** |
| Mass density | `g/cm^3` | $\rho = n_{\text{tot}} \sum f_k A_k / N_A$ |

故 `.cn4` 内的密度轴 `densnn` 是 **`cm^-3`**。转质量密度需乘平均原子量 `<A>`:

```
rho [g/cm3] = n_ion [cm^-3] · <A> [amu] / N_A
```

* **`<A>` 的权威来源** = **同目录 `ionmxinp` 文件**（`atomwt(i)` 行）。
  依据 `IONMIX用户指南.md:412`（`atomwt(i)` 第 i 种气体的原子量 (amu)）与 §4.1。
* `N_A` 的**唯一来源** = `config.N_A = 6.02214076e23`（`eosop_pro/config.py`），
  由 `cn4/units.py:111` 复用（`from ..config import N_A as NA`），
  **不在别处硬编码**（守护: `test_config_single_source.py::test_no_conversion_constant_hardcoded_outside_config`）。
* 原子量**缺失**时解析器**不给 `rho`**（`parsers/ionmix.py` notes 明写"不猜"）。

### 7.8 ⚠️ Fortran `E12.6` 字段溢出缺陷（**实测，非猜测**）

`E12.6` 仅能容纳 `0.ddddddE±ee` = **12 列**。当指数为 **3 位数**时
（`0.ddddddE-140`）需 **13 列**，Fortran 运行时**静默丢掉 `E`**，写出 `0.638380-140`。

**实证**（`src/.../matter++/Ionmix/h-imx-1grp.cn4`，`ntemp=17, ndens=21, ngrups=1`）:

| 检查项 | 结果 |
|---|---|
| 期望数值数 | **5395** |
| 严格 12 列切分 token 数 | **5395** ✅ 计数本就闭合 |
| 匹配打包指数模式的 token | **89** 个（`0.638380-140` … `0.201874-144`） |
| 修复后数值数 | **5395** ✅ 不变 |
| 修复后量级 | `1e-140`，正是该表压力/不透明度区的物理合理量级 |

**修复规则**（已在 `cn4_io.py::_PACKED_EXP_RE` 实现并注释）:

```
(\d\.\d{6})([-+]\d{3})   →   \1E\2
```

### 8.1 两种"自描述表头"范式（L2 的最佳范例）

`coldopacity`（实测 `ColdOpacity/Al.coldopacity`，67 个同类文件）:

```
Eph	miu          <- 第 1 行：列名（制表符分隔）
eV	cm2/g        <- 第 2 行：逐列单位（制表符分隔）
<空行>
10	486606.52638
```

这是全库**最直白的单位声明** —— 列名与单位各占一行、按列对齐。
另有 `hyades/coldopac.dat` 用另一套写法（`c` 开头注释 + `z = N` + 点数列）。

`hugoniot`（实测 `hyades/sesame/eos_41.hug`，157 行）:

```
# Rho[g/cm^3]  T [eV]         P [Mbar]  E [erg/g]      Us [km/s]      Up [km/s]
2.7059315e+000 2.6771096e-002 1.1245127e-002 3.9018342e+009 4.2385122e+000 ...
```

第 0 行是 `#` 注释，但**列名与单位都在方括号里** → 直接解析为轴/场的单位，
是"注释即证据"的又一例。

★ 第二种写法（实测于 `mat_Al-1.0/Al.feos.hug`）：括号里带**缩放因子**，例如
`Rho [1.000000e+000 g/cm^3]`、`P [1.000000e+012 dyne/cm^2]`。

### 8.2 `generic_curve` —— 保守兜底（**绝不猜测**）

适用于 `matter++` 里那些「无专门解析器、但明显是列式数值表」的文件，例如
`hyades/ionpot.dat`、`PowerLaws/*.dat`、`XrayMassCoef/*`、`Crystal/*.dat`、`Thermos/*.ini`。

策略（**保守，不猜测物理语义**）:
1. 剥离注释行（`#` / `%` / `c` 开头 / `REM`）
2. 统计各行的数值个数，取**众数**作为列数（非众数行 → 记录为异常，**不静默丢**）
3. 第 0 列作 x 轴，其余列命名为 `col1..colN`
4. 单位一律标 `unknown`，并把注释原文收集到 `notes` 供人工判定

> **绝不因文件名猜测物理量** —— 命名必须来自文档或注释证据。

### 8.3 ⚠️ `coldopacity` / `hugoniot` 的"设计性不确定"

这两族的单位**不在代码里硬编码**，而是从文件自身头部/注释**读出** ——
这是设计使然（不同实例可能用不同单位）。但若文件**未声明**，
解析器**不给单位**（`unit_source` 会显示实际来源）。这是**正确的保守行为**。

## 12. 其他类型 eosop 数据 → `.cn4` 的转换（**单位纪律**）

### 12.1 唯一入口

```
其他格式文件 → [各族 parser] → ParsedTable → parsed_tables_to_cn4() → .cn4 文件
```

* 入口函数: `eosop_pro.cn4.cn4_io.parsed_tables_to_cn4`
* 反方向: `cn4_to_parsed_tables()` 把 1 张 cn4 总表拆成 4 张 `ParsedTable`
  （1 张 EOS + 3 张不透明度），便于**按族**喂给 `parsed_tables_to_cn4`。
* 已验证: `cn4 → ParsedTable → cn4` **byte-identical**（无损往返）。
* `write_cn4` 与 `Ti-BADGER-TOPS.cn4`（2230155 字节）**逐字节相同**。

### 12.2 ⚠️ 单位纪律（转换时的硬约束）

1. `parsed_tables_to_cn4` **要求输入表带 `field_units`**。
2. 单位不匹配时**拒绝或显式警告**，**不会静默按错误单位写**。
3. `.cnr` **不能**作为来源 —— 它缺 12 个 EOS 场，无法补齐 cn4 的必需块。
4. 目标 `.cn4` 的 18 块单位**必须**是 §7.2 所列表格中的值
   （如压力必须为 `J/cm3`，**不是** `Mbar`）——
   由其他族（`Mbar` / `dyne/cm2`）转换时**必须显式换算**。

## 13. 结论

1. **支持 6 大格式族 / 17 个声明族**（分派见 `registry/dispatch.py` +
   `registry/declared_types.py`）。
2. **每个非 `unknown` 的单位都有可定位的「外部权威」出处** ——
   或为**源码行号**（`abjt_03.f`），或为**官方手册章节**
   （`Hyades 数据格式说明.doc`、`SNOP.MANUAL`、`MPQeos-JWGU-Documentation.pdf` 等），
   或为**数据文件内嵌声明**（L2）。**不再是"指向自己解析器"的循环论证。**
3. **每族都同时给出「溯源文档」与「实现脚本」两个字段**，
   二者职责分离：前者是**判定依据**，后者是**代码落点**。
4. **F6 IONMIX 是本项目单位最"特殊"的一族** —— 密度用**数密度 `cm^-3`**、
   压力/能量用 **SI 派生 `J/cm3` / `J/g`**，且 `.cn4` 与 `.cnr` 是**两种不同格式**，
   必须按**扩展名分派**。`.cnr` **未被用户指南文档化（检索命中 0）**，
   单位**仅有源码一个依据**。
5. **`unknown` 共 8 处，全部显式标注**，无一处靠猜测填充；
   另有 **1 处 `inferred`** 已注明推断依据。
