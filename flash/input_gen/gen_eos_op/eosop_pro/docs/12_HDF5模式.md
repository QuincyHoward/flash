# 12 · HDF5 模式（双轨）

> **用户的要求**：*"如何将一个物质的所有数据提取成统一网格的 h5 文件"* +
> *"额外一套统一 (rho, T_e[eV])、(nele, T_e[eV])、(nion, T_e[eV]) 网格插值"*。

本项目用**双轨（dual-track）**同时满足两个互相冲突的目标：

| 目标 | 轨道 | 满足它的性质 |
|---|---|---|
| **可回证**：能逐点核对回源文件 | `native/` | 原生网格**逐字**保留，含单位与 log10 标记 |
| **可直接用**：能当查找表用 | `unified/<gid>/` | 插值到统一网格，`(n_Te, n_x)` 定序 |

★ 只有一条轨都不够：只留 `native` 则每个下游都要自己处理格式差异；
只留 `unified` 则**无法验证插值对不对**（因为源数据没了）。
双轨的代价是约 2× 体积，收益是"可审查"。

## 1. 模式全貌（`schema_version = 1.0`）

```
/                                        attrs: schema_version, tool_version, generated_utc,
                                                material_name, family, declared_type,
                                                source_relpath, A_amu, n_tables,
                                                native_track, unified_track,
                                                nan_semantics, grid_convention, pipeline, stage

/meta/sources              [n_tables × 20]   溯源表（每张表一行）
/meta/annotations          [n_files  × 14]   注释证据（伴随文件/内联声明）
/meta/units                [k        ×  4]   (quantity, unit, 来源) 逐条
/meta/warnings             [m]               全部告警
/meta/unified_grids/<gid>/                    attrs: x_axis, x_min, x_max, n_x,
                                                     Te_min_eV, Te_max_eV, n_Te,
                                                     spacing, nan_semantics, A_amu
/meta/zeff_sources         [n_z × 7]         Z̄ 来源

/tables/<KIND>_<key>/                         attrs: 见 §2.1
    group_bounds_eV        [ng+1]            多群边界（仅多群表有）
    native/                                   轨道 1：原生网格逐字
        <axis_name>        [n]                attrs: units, log10, axis=True, n
        <field_name>       [shape]            attrs: units, log10, axis=False, shape
    unified/<gid>/                            轨道 2：统一网格插值
        x                  [n_x]              x 轴（rho 或 n_ion）
        Te                 [n_Te]             Te 轴
        rho_of_x           [n_x]              （仅 F1 反演表）x 对应的原生 rho
        <field>            [n_Te, n_x]        attrs: units, log10=False,
                                                     interp_method, extrapolation,
                                                     out_of_range_count, coverage
```

### 1.1 表键命名

```python
table_key = f"{KIND}_{id}"     # 例：ROSSELAND_1041、ZEFF_27002003、EOS_37181000
                               #     OPACITY_1031、PLANCK_0、MUGROUP_27004003
```

`KIND` 优先来自 `material.base` 的引用键（`EOS`/`PLANCK`/`ROSSELAND`/`ZEFF`/
`NONLTE`），其次来自文件名 token，再次来自 SESAME 表号位（[03 §4.1](03_注释证据通道.md)）。

### 1.2 统一约定

| 项 | 约定 |
|---|---|
| 物理量 dtype | 一律 `float64` |
| 2D 场轴序 | **固定 `(n_Te, n_x)`** —— 温度是第一维，与 `ParsedTable.field_shape` 一致 |
| 压缩 | `gzip level=4 + shuffle`；2D/3D 显式 `chunks`；1D 轴**不压缩**（太小，压缩反而增大） |
| 分块尺寸 | `chunks = min(shape_i, 64)` |
| **NaN 语义** | `nan_semantics = "out_of_range"` —— NaN **只**表示"落在原生凸包之外"，与"值恰为 0"严格区分 |
| 字符串表 | 变长 UTF-8（`object` 数组 + `string_dtype()`），列名存在 `attrs["columns"]` |

★ **NaN 语义是全项目最重要的一条约定**。如果 NaN 既表示"越界"又表示"缺失"，
下游就无法判断"这个点是物理上不存在"还是"我们没算出来"。
所以：

- 越界 → `NaN`（真实语义）
- 源数据里的 `NaN`/`inf`（如 MSVC 的 `-1.#INF`）→ 也写 `NaN`，
  但**同时在 `/meta/warnings` 里记一条"上游数据缺陷"**
- 源的 `0` → 写 `0`（不改）

## 2. 属性清单（可核验字段）

### 2.1 `/tables/<KIND>_<key>/` 的属性

```python
S.scalar_attrs(
    table_key, quantity_kind, family, source_relpath, table_id, sesame_digit,
    f2_or_label, header_raw, layout_rule, unit_source, n_groups,
    n_native_x, n_native_Te, n_numbers_seen, n_numbers_expected,
    axis_order="['Te_eV','x']",
)
# 另加：
#   native_units_<axis/field>   ← 每个轴与场的单位
#   notes                        ← 解析器 notes（截前 20 条）
#   has_native_track / has_unified_track
```

`layout_rule` 与 `unit_source` 是**两条最值钱的可核验字段**：

```
layout_rule : "F1/with_e0: 4 + 2*nr + ne + 2*nr*ne"
unit_source : "format:F1 (rho g/cm3, P Mbar, T Kelvin->eV)"

layout_rule : "F3: L = 2 + nr + nt + 2*nr*nt"
unit_source : "format:F3 (rho g/cm3, T keV->eV, P dyne/cm2, E erg/g)"
```

任何人拿到 h5 都能从这两条字符串知道"计数公式是什么、单位是怎么换算的"。

### 2.2 `native/` 的属性（每个数据集）

| 属性 | 含义 |
|---|---|
| `units` | 该轴/场的单位（`g/cm3`、`eV`、`Mbar`、`cm2/g`、`unknown`…） |
| `log10` | **bool**：存的是 log10 值还是物理量 |
| `axis` | **bool**：是坐标轴（`True`）还是依赖量（`False`） |
| `n` / `shape` | 长度 / 形状字符串 |

★ `log10` 标记必填。F2 的 `kappa` 与轴都是 log10 存储，
F1/F3/F4 是线性存储。**混在一张 h5 里只有这个标记能区分。**

### 2.3 `unified/<gid>/` 的属性

| 属性 | 含义 |
|---|---|
| `x_axis` | `"rho"` 或 `"n_ion"` |
| `interp_method` | `"bilinear_log10"` 或 `"invert-(rho,de)->(rho,Te) + log10-bilinear"` |
| `extrapolation` | `"nan"` / `"clamp"` / `"linear"` |
| `out_of_range_count` | 越界点数（**质量指标**） |
| `coverage` | 有效点占比（**质量指标**） |
| `A_amu` | 换算用的原子量（`nion_Te` 轨才有） |
| `origin` | 某些场的来源标记（如 `"inverted-from-(rho,de)"`） |

`out_of_range_count` 与 `coverage` 让"插值质量"变成**可查的数**，
而不是"看起来还行"。

## 3. 一条完整的写出路径

以 `mat_Al-1.0/AL_eos` 为例：

```
cli h5 mat_Al-1.0/AL_eos --out al.h5
  │
  ├─ 1. declare()            → 家族 multi_inverted_eos
  ├─ 2. parse_declared()     → ParsedTable
  │      axes   rho(66), de(74)
  │      fields P(74,66) E(74,66) T(74,66) e0_cold(66) de_energy(74)
  │      unit_source "format:F1 (rho g/cm3, P Mbar, T Kelvin->eV)"
  ├─ 3. A = _A_for(rel)      → 26.982（从 material.base）
  ├─ 4. build_all_grids()    → {rho_Te: g1, nion_Te: g2}
  │      共用 Te 轴（128 点 log 等距，取原生 Te 范围∩物理包络）
  │      x 轴：rho 128 点 / n_ion = rho·N_A/Ā 128 点
  ├─ 5. write_material_h5()  → 双轨
  │      write_native()      → 逐字
  │      write_unified()
  │        is_de_based == True → _write_unified_from_de_table()
  │          to_Te_grid(table, g.Te, fields=("P","E","T"))
  │          → 反演成 (rho, Te) 网格上的场
  │        sub.attrs["origin"] = "inverted-from-(rho,de)"
  └─ 6. 返回 Path
```

第 5 步的分支是全项目最关键的一处：

```python
def write_unified(f, table, grids, *, A=None, skip_inverted_eos=False):
    is_de_based = "de" in table.axes and "Te" not in table.axes
    for gid, g in grids.items():
        if is_de_based:
            n_oor = _write_unified_from_de_table(sub, table, g)
            note = "invert-(rho,de)->(rho,Te) + log10-bilinear"
        else:
            n_oor = _write_unified_from_te_table(sub, table, g, A)
            note = config.INTERP_METHOD
```

**F1（`de` 基）必须先反演再插值** —— 详见 [13 §5](13_统一网格与插值.md)。

## 4. 两处"静默出错"的修复

### 4.1 `kappa` 二次取 log10 → NaN

初版 `_source_2d()` 对 F2 的 `kappa` 又做了一次 `log10`：

```python
# ❌ 初版
arr = np.log10(arr)      # 但 arr 已经是 log10 值了！
                         # → log10(负值) = NaN，实测误差 5.655
```

修法：

```python
is_log = bool(table.field_log10.get(field, False))
if is_log:
    arr = np.power(10.0, arr)     # ★ 先还原成物理量
return rho, Te, arr, is_log       # 并把 log_value 传给插值
```

即 **"还原成物理量 → 在 log 空间插值 → 写物理量（`log10=False`）"**。
这样 h5 里"存的是 log 还是物理量"**只有一个答案**，不会出现
"有的数据集是 log、有的是物理量"的混乱。

### 4.2 `nion_Te` 的 x 轴写成了 `rho`

```python
# ❌ 初版：源 x 直接用 rho
res = interp.resample_2d(rho_src, Te_src, arr, g.x, g.Te, ...)
#                          ↑ rho                ↑ 但 g.x 是 n_ion！
```

症状：`nion_Te` 轨的数值"看起来合理"（因为都是单调递增的量），
但**等于拿两把不同的尺子量**，数值系统性错位。

修法：**源 x 必须做与目标 x 相同的变换**：

```python
# ✅
x_src = np.array([x_from_rho(g.gid, r, A) for r in rho_src], dtype=float)
res = interp.resample_2d(x_src, Te_src, arr,
                         np.asarray(g.x, dtype=float),
                         np.asarray(g.Te, dtype=float),
                         logs=("x", "y"), log_value=log_v)
```

这条修复在 `test_batch.py::test_convert_all_dual_track_keeps_native_verbatim_and_unified_grids`
里有直接断言：`nion_Te` 的 `x_axis` 必须是 `"n_ion"`。

### 4.3 ★ 文件命名：222 个 h5 曾被静默覆盖

```python
# ❌ 初版：`stem` 切掉了最后一个点之后的部分
stem   = Path(d.relpath).stem
parent = Path(d.relpath).parent.as_posix().replace("/", "__")
h5_name = f"{parent}__{stem}.h5"
```

后果（实测，**7 个 ATOMIC 文件共享一个输出名**）：

```
ATOMIC/Al.txt                          → ATOMIC__Al.h5
ATOMIC/Al.NoFree                       → ATOMIC__Al.h5   ← 覆盖
ATOMIC/Al.AvSqFree                     → ATOMIC__Al.h5   ← 覆盖
ATOMIC/Al.GrayOpacity_PLANCK           → ATOMIC__Al.h5   ← 覆盖
ATOMIC/Al.GrayOpacity_ROSSELAND        → ATOMIC__Al.h5   ← 覆盖
ATOMIC/Al.MultiGroupOpacity_PLANCK     → ATOMIC__Al.h5   ← 覆盖
ATOMIC/Al.MultiGroupOpacity_ROSSELAND  → ATOMIC__Al.h5   ← 覆盖
```

全树：**78 个名字被复用，222 个文件被覆盖** —— 而 `convert-all` 报 `n_failed=0`，
`write_material_h5` 每次都"成功"（覆盖**不报错**）。

修法：

```python
def _h5_name_for(relpath: str) -> str:
    """由相对路径生成**唯一**的 h5 文件名：目录 → `__`，**所有**点号 → `_`。"""
    s = str(relpath).replace("\\", "/").replace("/", "__").replace(".", "_")
    s = re.sub(r"[^0-9A-Za-z_\u4e00-\u9fff-]+", "_", s)
    return f"{re.sub(r'_{3,}', '__', s).strip('_') or 'file'}.h5"
```

```
ATOMIC/Al.NoFree          → ATOMIC__Al_NoFree.h5
ATOMIC/Al.txt             → ATOMIC__Al_txt.h5
hyades/sesame/eos_41.dat  → hyades__sesame__eos_41_dat.h5
mat_Al-1.0/AL_eos         → mat_Al-1_0__AL_eos.h5
```

再加两道保险：

1. `_check_name_collisions(relpaths)` —— 万一命名规则被改坏，
   **加数字后缀而不是覆盖**（`same_2.h5` / `same_3.h5`）。
2. **与磁盘对账**：

```python
n_on_disk = len(list(od.glob("*.h5")))
if n_on_disk < n_written:
    msg = (f"⚠️ h5 命名冲突：报告 n_written={n_written}，"
           f"但盘上只有 {n_on_disk} 个 .h5 —— {n_written - n_on_disk} 个被覆盖！")
```

对账结果写进报告头部（`对账: 盘上 .h5 数 == 已写数 → ✅ 通过`）、
JSON（`n_h5_on_disk` / `reconciled`）与函数返回值。

★ **这条 bug 只有靠"报告的数"与"磁盘上的事实"对账才能发现** ——
`audit` 不写 h5、`identify` 不写 h5、异常与日志全都没有。
详见 [14 §4.1](14_审计报告.md)。

`plot-all` 的图名用同一套命名（`_h5_name_for(rel)[:-3]`），
避免 7 个 ATOMIC 文件的图互相覆盖。

## 5. 单表 / 材料级 / 批量三种入口

| 入口 | 函数 | tables 数 | grids | 用途 |
|---|---|---|---|---|
| **单表** | `convert.write_h5_single` | 1 | 两套（可关） | 交互式排查 |
| **材料级** | `writer.h5_writer.write_material_h5` | N | 两套（可关） | 一个材料一个 h5 |
| **批量** | `batch.convert_all` | 按声明分组 | 两套（可关） | 全树 |

`write_h5_single` 与 `write_material_h5` **共用同一个 schema 与写出函数** ——
没有"单表用一套格式、材料级用另一套"的分裂。

### 5.1 批量入口的两个过滤轴

```python
batch.convert_all(outdir=..., report_dir=...,
                  only_families=("multi_opacity",),      # 按家族
                  only_relpaths=["Thermos/mat_Mo/Mo_Ideal_Gas",
                                 "mat_Al-1.0/AL_eos"],   # ★ 按文件（顺序显式）
                  limit=0,                               # 0 = 不设上限
                  include_multigroup=False,              # LEDCOP 多群默认关
                  with_native=True, with_unified=True)
```

`only_relpaths` 给定时**按给定顺序处理**，不受全树扫描顺序影响 ——
使"精确复现某个文件"成为可能（回归测试就靠它，不必跑全树）。

★ 另外 `report_dir` 是独立于 `outdir` 的：测试传临时目录，
**避免跑测试时污染真实的 `outputs/reports/`**（这条是实测踩出来的：
加测试前 `outputs/reports/` 里堆了 133 个文件，绝大多数来自 test 运行）。

### 5.2 轨道开关（`native_track` / `unified`）

```python
write_material_h5(out, material=..., tables=..., grids=None,
                  native_track=False)      # 只有 unified
```

★ 两条轨**都关**会被显式拒绝：

```python
if not native_track and not grids:
    raise ValueError("write_material_h5: native_track=False 且 grids=None "
                     "—— 两轨都关会写出空文件")
```

这是把"没有意义的调用"变成**早期失败**，而不是产出一个 0 字节 h5。

实测（`test_batch.py` 的 3 条断言）：

```bash
convert-all --limit 2 --native-only    # → 只有 native/，无 unified/
convert-all --limit 2 --unified-only   # → 只有 unified/，无 native/
```

## 6. 读取示例

```python
import h5py, numpy as np

with h5py.File("al.h5") as f:
    # 溯源
    print(f.attrs["source_relpath"], f.attrs["pipeline"])
    print(dict(zip(
        f["meta/units"].attrs["columns"].split(", "),
        f["meta/units"][0].tolist())))

    # native 轨：逐字
    g = f["tables/EOS_37181000"]
    print(g["native/rho"].attrs["units"],   # 'g/cm3'
          g["native/rho"].attrs["log10"])   # False
    P_native = g["native/P"][:]             # (nt, nr) = (74, 66)

    # unified 轨：可直接当查找表
    u = g["unified/rho_Te"]
    Te = u["Te"][:]                         # (128,) eV
    x  = u["x"][:]                          # (128,) g/cm3
    P  = u["P"][:]                          # (128, 128)  ← (n_Te, n_x)
    print(u.attrs["out_of_range_count"], u.attrs["coverage"])

    # 双线性查表（log 空间）
    def lookup(rho, Te_v, field="P"):
        i = np.searchsorted(np.log10(x), np.log10(rho))
        j = np.searchsorted(np.log10(Te), np.log10(Te_v))
        return u[field][j, i]
```

★ 最后那段 `lookup` 直接说明了**为什么轴序是 `(n_Te, n_x)`**：
`u[field][j, i]` 与 `searchsorted(axis_Te)[j]`、`searchsorted(axis_x)[i]`
一一对应，不用记"谁是行谁是列"。

## 7. 与跨格式转换的关系

HDF5 不只是"最终产物" —— 它也是 `ConverterRegistry` 里的**一个目标**
（`name="h5"`）：

```python
register(ConvertTarget(
    name="h5",
    description="HDF5 单表（双轨：native 逐字 + unified 两套统一网格）",
    writer=write_h5_single,
    requires=("*",),              # 任何表都能写
))
```

于是**跨格式转换与落盘用的是同一条管线**：

```
read(A) → ParsedTable → write(B)        # B 可以是 h5，也可以是 hyades_eos
```

已注册目标（`cli targets` 可列）：

| name | 说明 |
|---|---|
| `multi_opacity` | 逆变换 F2（灰度 / 多群子表串联） |
| `hyades_eos` | 逆变换 F3（`L=2+nr+nt+2·nr·nt`，T 以 **keV** 写出） |
| `multi_inverted_eos` | 逆变换 F1（`with_e0` / `no_e0` 自动判） |
| `h5` | 单表 HDF5（双轨） |

★ **新增一个目标格式 = 写一个 `write_x(table, path, **opts)` + `register(...)`**，
不需要为每一对 (源, 目标) 写转换器。这就是 [01 §3.2](01_总览.md) 说的
"为后期不同文件格式的相互转换留下接口"。

实测往返（F1 → F3 → 回读）：

```
EOS_37181000 -> hyades_eos: outputs/logs/t3.dat
re-parsed: EOS_37181000 66 74 9910
L = 2 + 66 + 74 + 2·66·74 = 9910  ✅
```

## 8. 测试覆盖

`test_h5_schema.py`（10 个）+ `test_batch.py` 的 5 个双轨测试：

| 测试 | 断言 |
|---|---|
| 模式常量 | `/meta`、`/tables`、`native`、`unified` 路径与属性名 |
| 必填属性 | `REQUIRED_TABLE_ATTRS` / `REQUIRED_AXIS_ATTRS` / `REQUIRED_FIELD_ATTRS` 全部存在 |
| 轴序 | 2D 场一律 `(n_Te, n_x)` |
| 压缩 | 2D 有 `chunks` + `gzip` + `shuffle`；1D 轴不压缩 |
| NaN 语义 | `nan_semantics == "out_of_range"` |
| 双轨存在性 | 每张表都有 `native/`；至少一张有 `unified/` |
| `nion_Te` 轴 | `x_axis == "n_ion"`（**回归**：x 轴变换一致性） |
| 单轨 | `--native-only` / `--unified-only` 各自只写一条轨 |
| 双关拒绝 | `native_track=False` + `grids=None` 抛 `ValueError` |
| 往返 | F1 → F3 → 解析回读，维度与计数一致（`L=9910`） |
