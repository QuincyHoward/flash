# 15 · 单位换算

> 这是全项目**最容易出错、后果最隐蔽**的一块。
> 一个常数因子写错，数据长得完全正常 —— 只是错了 1000 倍。

## 2. 为什么必须靠"声明"而不是"推断"

### 2.1 实测反例：`Al_Zeff.dat` vs `Al_Z.dat`

```
Thermos/mat_Al/Al_Zeff.dat      128 行，logT 区间 [a, a+3]
Thermos/mat_Al/Al_Z.dat         128 行，logT 区间 [a, a+3]
```

两者的**表头、行数、区间长度完全相同**，`log10` 值只差

```
log10(1000) = 3.000
```

从纯数字看，两个文件都是"合法的 log 网格"。
**没有任何数值证据能区分哪个是 eV、哪个是 keV。**

可靠区分只能来自**声明** —— 而上游恰好留下了这段说明
（`docs/extracted/MULTI使用的SESAME数据文件格式__ooxml-word__3e289d7f.txt`）：

> 注：之前的 Multi 计算中一直发现电离度偏高，况龙钰(20160109)发现是**温度的单位弄错了**，
> SNOP 等输出的 SESAME 数据，温度的单位一直是 **keV**。但是在 Multi 的输入是按照
> **eV** 输入的，因此导致电离度明显偏高。
>
> 因为之前(20160109)的计算中按照 eV 输入，因此在创建 Thermos 的数据文件时电离度也是
> 按照 eV 创建的，不存在偏大的情况。但程序自 20160109 之后，统一将输入按照 keV 执行；
> 相应的 Thermos 文件夹中所有的电离度文件(**名字为 `X_Z.dat`**) 温度按照 keV 重新生成，
> 以使其格式与 SNOP 等 SESAME 格式一致。**名字为 `X_Zeff.dat`(温度单位为 keV)**，
> 以与之前的 `X_Z.dat`(温度单位为 eV) 相区分。
> `Material.base` 中替换所有 `X_Z.dat` 为 `X_Zeff.dat`。

★ ⚠️ **原文最后一层表述有一个内部矛盾**：前文说"`X_Z.dat` 温度按照 keV 重新生成"，
但紧接着说 `X_Zeff.dat` 是 keV、`X_Z.dat` 是 eV。

本项目的处置是**以"区分"这一功能性陈述为准**：

| 文件 | 裁定单位 | 依据 |
|---|---|---|
| `*_Zeff.dat` | **keV** | 原文功能句：`X_Zeff.dat`(温度单位为 keV) |
| `*_Z.dat` | **eV** | 原文功能句：以与之前的 `X_Z.dat`(温度单位为 eV) 相区分 |
| 且二者都被 `material.base` 引用过（`X_Z.dat` → 替换为 `X_Zeff.dat`） | | |

这条矛盾**不说破是不诚实的**，所以写在这里，并在
`test_zeff_registry.py::test_thermos_zeff_is_keV_and_z_is_eV_by_declaration`
里固化成断言 —— 一旦上游修正文档，测试会提醒我们更新。

### 2.2 包络反演的**两个盲区**

```python
LOG_T_EV_IF_GE  = 4.5     # log10(T) >= 4.5 → 一定是 eV 量级
LOG_T_KEV_IF_LE = 2.5     # log10(T) <= 2.5 → 一定是 keV 量级
```

这两组阈值实测**无重叠**（eV 网格的 `log10(T)` 在 `[0,6]`，
keV 网格在 `[-3,3]`），所以对**大多数**文件包络判定是有效的。

但它有两个致命盲区：

| 盲区 | 说明 | 后果 |
|---|---|---|
| **常数因子不可辨** | `Al_Z` 与 `Al_Zeff` 的 `log10` 恰差 3.000，都落在 `[0,6]` 内 | 包络判不出谁是谁 |
| **低端越界** | 某 eV 网格的低端 `1e-2 eV`（`log10=-2`）落在 keV 区间 | 单点判据会误判 |

所以判据必须是**整个网格的趋势**（中位数或 `log10(max)`），不是单点；
而且包络**只能排在第 3 位**（在 `companion` / `inline` 之后）。

## 3. 四级仲裁链

```python
"""裁决优先级（高 → 低）
1. companion      —— 伴随注释文件的**文件名模式**声明
                     （Thermos/Readme.txt 明写 *_Z.dat=eV、*_Zeff.dat=keV）
2. inline         —— 文件内嵌单位声明
                     （ATOMIC/*.txt 的 `T in keV`、.coldopacity 的两行表头、
                       mat_Ge/Readme.txt）
3. envelope       —— 兜底启发式：由 logT 上限判断（≥4.5 → eV；≤2.5 → keV）
                     并在换算后用**物理包络** T ∈ [1e-2, 1e6] eV 复核
4. config_default —— 格式默认（如 F2 默认 eV）

每条裁决都带 source 与 evidence，写进 h5 的 /meta/units，
使「为什么取这个单位」可追溯。
"""
```

```python
@dataclass
class UnitDecision:
    quantity: str         # "T" | "rho" | "P" | "E" | "kappa" | "Z"
    unit: str             # "eV" | "keV" | "g/cm3" | "Mbar" | "cm2/g" | "unknown"
    source: str           # companion | inline | envelope | config_default | unknown
    evidence: str = ""    # ★ 判定依据的原文/模式
```

**`evidence` 是这条链最值钱的字段**。例如：

```
("T", "keV", "companion",
 "Thermos/Readme.txt: 'X_Zeff.dat(温度单位为 keV)' → 文件名模式 *_Zeff.dat")
("T", "keV", "inline",
 "ATOMIC/Al.txt: 'Opacities in cm**2/gm, T in keV, density in gm/cc'")
("T", "eV",  "config_default",
 "F2 族默认（无针对性声明）")
```

## 4. 换算常量（`config.py`）

```python
N_A            = 6.02214076e23        # mol^-1
EV_PER_K       = 8.617333262e-5       # eV/K       ← F1 的 Kelvin → eV
K_PER_EV       = 1.0 / EV_PER_K
KEV_PER_EV     = 1e-3
MBAR_PER_GPA                = 1e-2    # 1 GPa = 1e-2 Mbar      ← F4
MBAR_CM3_G_PER_MJ_KG        = 1e-2    # 1 MJ/kg = 1e-2 Mbar·cm3/g ← F4
ERG_G_PER_MBAR_CM3_G        = 1e9     # 1 Mbar·cm3/g = 1e9 erg/g
DYN_CM2_PER_MBAR            = 1e12    # 1 Mbar = 1e12 dyne/cm2
AMU_G                       = 1.66053906660e-24   # g   ← nion 换算
```

★ **全项目只允许在这一个文件里写数字**。这条纪律**由测试强制执行**，不是靠自觉：
`test/test_config_single_source.py` 用 `ast` 解析 `eosop_pro/` 下每个模块，
收集所有 float 字面量并与上表逐一比对，命中即失败。

分两档是为了**避免假阳性**：

| 档 | 常量 | 判据 |
|---|---|---|
| **distinctive** | `EV_PER_K`、`N_A`、`AMU_G` | 值匹配即失败（有效数字多位，不可能巧合） |
| **round** | `MBAR_PER_GPA`、`MBAR_CM3_G_PER_MJ_KG`、`DYN_CM2_PER_MBAR`、`KEV_PER_EV`、`ERG_G_PER_MBAR_CM3_G` | 值匹配 **且** 同行出现单位词才失败 |

为什么要分档：实测 `plotting/qa_plots.py` 的
`densities=(0.01, 0.1, 1.0, 10.0)` 里的 `0.01` 与 `MBAR_PER_GPA` 值相同，
但它表示"要画哪几条等密度线"，与单位换算无关。
只按值匹配会产生假阳性，进而让人把检查关掉 —— 那还不如没有检查。
这条假阳性已固化为回归测试
`test_round_tier_does_not_false_positive_on_plot_defaults`。

用 `ast` 而不是正则的另一个好处：`ast` **天然跳过 docstring 与注释**
（它们是 `str` 常量而非 `float`），所以文档里写 `≈ eV / 8.617e-5`
这种说明文字不会误报 —— 否则为了过测试就不能在注释里解释物理。

### 4.1 上游给出的三条换算关系（逐字）

```
压力：     1GPa = 1e9Pa = 1e10 dyne/cm2 = 1e10 erg/cm3 = 1e12 erg/cm2 = 1e-2 Mbar
能量密度： 1MJ/kg = 1e3 J/g = 1e10 erg/g = 1e12 erg*cm/g = 1e-2 Mbar*cm3/g
比内能：   1 Mbar*cm3/g = 1e9 erg/g
```

★ 上游原文写的 `dyne/cm2` 对应 `Mbar` 时是 `1e12`；
写的 `erg/cm2` 那一项是**原文笔误**（应为 `erg/cm3`）。
本项目以 **量纲自洽**为准：

```
1 Mbar = 1e6 dyn/cm² × ...  → 1e12 dyne/cm²   ✅（DYN_CM2_PER_MBAR = 1e12）
1 Mbar·cm³/g = 1e12 dyn/cm² · cm³/g = 1e12 erg/g   ✅
```

### 4.2 `EV_PER_K` 的精度

CODATA 2018 的 `k_B = 1.380649e-23 J/K`，
`eV = 1.602176634e-19 J` → `EV_PER_K = 1.380649e-23 / 1.602176634e-19
= 8.617333262e-5 eV/K`。全 10 位有效数字，与 `config` 一致。

## 5. 换算发生在哪一层（逐族）

### 5.1 F1：Kelvin → eV

```python
# parsers/multi_inverted_eos.py
table.fields["T"] = [t * config.EV_PER_K for t in T_K]
table.field_units["T"] = "eV"
table.unit_source = "format:F1 (rho g/cm3, P Mbar, T Kelvin->eV)"
```

★ `unit_source` 字符串里的 `T Kelvin->eV` 就是**换算的痕迹**。
它同时：
- 说明"文件里本来是 Kelvin"（审计需要）
- 说明"我已经换算过了"（下游不需要再换）

### 5.2 F3：keV → eV

```python
T_scale = {"kev": 1e3, "ev": 1.0}.get((unit_hint_T or "keV").lower(), 1e3)
table.axes["Te"] = [t * T_scale for t in T_keV]
table.axis_units["Te"] = "eV"
table.unit_source = "format:F3 (rho g/cm3, T keV->eV, P dyne/cm2, E erg/g)"
```

`unit_hint_T` 来自伴随文件/内联注释；缺省按族约定 `keV`，
但缺省这件事**体现在 `unit_source` 里**（没有 `companion:` / `inline:` 前缀即可看出）。

### 5.3 F4：GPa→Mbar、MJ/kg→Mbar·cm³/g、Kelvin→eV

```python
table.unit_source = "format:F4 (GPa->Mbar, MJ/kg->Mbar*cm3/g, T Kelvin->eV)"
table.field_units["P"] = "Mbar"
table.field_units["E"] = "Mbar*cm3/g"
table.axis_units["Te"] = "eV"
```

★ **三处换算的落点都写进同一个字符串**，一眼可见。

### 5.4 F5：keV → eV（**声明来的**）

```python
# unit_hint_T 来自 ledcop_units 锚点：
#   "Opacities in cm**2/gm, T in keV, density in gm/cc"
```

因为证据是**内联声明**，`unit_source` 前缀是 `inline:` 而不是 `default:`，
快照状态是 `ok` 而不是 `ok_unverified`。

### 5.5 F2 的 Z̄：`default:eV` + 显式预警

```python
table.unit_source = ("default:eV (⚠️ ZEFF 表存在 eV/keV 两套，"
                     "应由注释声明)")
```

★ 这是**唯一**一个把"缺证据"写进 `unit_source` 的地方。
这条字符串会一路带到 HDF5 与审计报告，使"这个文件单位未定案"
在任何一层都可见。

## 6. 单位的"下游后果"

### 6.1 单位错了会怎样（真实后果清单）

| 场景 | 后果 | 是否可察觉 |
|---|---|---|
| Z̄ 表 T 单位错（eV 当 keV 用） | 电离度**系统性偏高**（上游 2016-01-09 记录的真实事故） | ❌ 数值"看起来合理" |
| F1 的 T 当 eV 用 | 温度偏高 `1/8.6e-5 ≈ 1.16e4` 倍 | ❌ 曲线形状不变 |
| F4 的 P 当 Mbar 用（实为 GPa） | 压强偏小 100 倍 | ❌ |
| F4 的 E 当 erg/g 用（实为 MJ/kg） | 比内能偏小 1e10 倍 | ⚠️ 可能被包络拦下 |
| `hugoniot` 的缩放因子被忽略 | P 差 `1e12` 倍 | ❌ |

★ 共同点：**除最后一个，全部无法从数值本身察觉**。
这就是为什么单位必须走"声明优先"的独立裁决链，而不是"解析器顺手判一下"。

### 6.2 `hugoniot` 的缩放因子：一个特别危险的例子

```
Rho [1.000000e+000 g/cm^3]  P [1.000000e+012 dyne/cm^2]
```

括号里第一个数是**该列的缩放倍数**。如果只把它当单位字符串里的一段：

```python
# ❌ 错：整个 "1.000000e+012 dyne/cm^2" 当单位
field_units["P"] = "1.000000e+012 dyne/cm^2"    # 非标准单位串
# → 下游假设 P 是 dyne/cm²，但实际值已经是 Mbar 量级 → 差 1e12
```

修法：

```python
_SCALE_UNIT_RE = re.compile(r"^\s*([-+]?[\d.]+(?:[eE][-+]?\d+)?)\s+(\S.*)$")
#                               ↑ 缩放因子                        ↑ 单位
```

拆出 `(scale, unit)` 后：
- `field_units[name] = unit`（标准单位）
- `scale` 记进 `notes`，**不自动乘进数值**

★ **不自动缩放**是有意的：改了数值就破坏"native 轨逐字保留"的契约。
缩放因子作为**元数据**交给下游，由下游决定怎么用。

### 6.3 `nion_Te` 网格的换算（`N_A` 与 `A`）

```python
def x_from_rho(gid, rho, A):
    if gid == "nion_Te":
        return rho * config.N_A / A      # 1/cm³
```

`A` 从 `material.base` 取（实测 Al → `26.982`）。
`A is None` 时**跳过该轨**并记 warning —— **不猜**一个默认原子量。

量纲检查：
```
ρ [g/cm³] × N_A [1/mol] / A [amu]
= ρ × 6.022e23 / 26.982     （A 的数值即 g/mol，amu 与 g/mol 数值相等）
≈ 2.231e22 /cm³             （Al 在 ρ=1 g/cm³ 时）
```

Al 离子数与密度 → `n_ion ≈ 2.23e22 cm⁻³`（对 ρ=1）。数量级正确。
